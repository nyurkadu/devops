# 8. Эндпоинты меняются динамически

Задание: **Убедиться на практике, что эндпоинты динамически меняются (добавляются и удаляются).**

В миссии 7 состав сервиса проверялся «снимками» — до и после действия. Здесь задача другая: увидеть **сам процесс изменения**, поэтому все сценарии сняты через `kubectl get ... -w` (watch) с проставленной меткой времени:

```bash
( kubectl get endpoints svc-demo-svc -w | while IFS= read -r l; do echo "$(date +%T) | $l"; done ) &
```

## Доработка стенда

К [07_svc-demo.yaml](07_svc-demo.yaml) добавлены `preStop`-хук и явный grace period — без них nginx умирает мгновенно и состояние «под завершается, но ещё обслуживает» проскакивает незаметно:

```yaml
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: nginx
          ...
          # задержка перед остановкой: под успевает побыть в состоянии Terminating,
          # и видно, как эндпоинт помечается terminating до фактической смерти пода
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "15"]
```

Также используется `EndpointSlice` — в отличие от старого объекта `Endpoints`, он хранит для каждого адреса три отдельных флага:

```bash
kubectl get endpointslice -l kubernetes.io/service-name=svc-demo-svc -w \
  -o custom-columns='ADDR:.endpoints[*].addresses[0],READY:.endpoints[*].conditions.ready,SERVING:.endpoints[*].conditions.serving,TERM:.endpoints[*].conditions.terminating'
```

| Флаг | Значение |
|---|---|
| `ready` | можно направлять **новые** соединения |
| `serving` | под фактически обслуживает (readiness проходит) — остаётся `true` даже во время завершения |
| `terminating` | под получил сигнал на остановку |

## A. Масштабирование: эндпоинты добавляются и удаляются

kubectl scale deploy/svc-demo --replicas=5     # затем обратно на 2

**Наблюдения:**
- Объект `Endpoints` **переписывается при каждом изменении** — за 3 секунды после `scale` прошло 5 отдельных обновлений. Никакой ручной синхронизации: контроллер эндпоинтов реагирует на появление/готовность подов.
- Первые два обновления (18:40:44 и 18:40:45) внешне не изменили список: новые поды уже существовали, но ещё не были `Ready`, поэтому их IP попали в `notReadyAddresses`, а не в основной список.
- Добавление растянуто на ~3 c (поды поднимаются по очереди), а **удаление произошло за 1 секунду**: как только реплики помечены на снос, их адреса убираются сразу, не дожидаясь фактической смерти подов.

## B. Удаление пода: полный жизненный цикл эндпоинта

```bash
kubectl delete pod svc-demo-779979d447-brcz6 --wait=false
```

```
18:42:02 | ADDR                                    READY              SERVING           TERM
18:42:02 | 10.244.0.86,10.244.0.87                 true,true          true,true         false,false
>>> 18:42:05 kubectl delete pod svc-demo-779979d447-brcz6
18:42:05 | 10.244.0.86,10.244.0.87                 true,false         true,true         false,true
18:42:07 | 10.244.0.86,10.244.0.87,10.244.0.88     true,false,false   true,true,false   false,true,false
18:42:07 | 10.244.0.86,10.244.0.87,10.244.0.88     true,false,true    true,true,true    false,true,false
18:42:22 | 10.244.0.86,10.244.0.88                 true,true          true,true         false,false
```

Хронология по адресу `10.244.0.87` (удаляемый под):

| Время | Событие | `ready` | `serving` | `terminating` |
|---|---|---|---|---|
| 18:42:02 | норма | `true` | `true` | `false` |
| 18:42:05 | **в ту же секунду** после `delete` | `false` | `true` | `true` |
| 18:42:22 | через 15 c (отработал `preStop`) | адрес **удалён из слайса** | | |

Параллельно — жизнь замены `10.244.0.88`:

| Время | Событие | `ready` | `serving` |
|---|---|---|---|
| 18:42:07 | ReplicaSet создал под, эндпоинт заведён | `false` | `false` |
| 18:42:07 | readiness прошла | `true` | `true` |

**Наблюдения:**
- Эндпоинт удаляемого пода **не исчезает мгновенно** — он сначала переходит в промежуточное состояние `ready=false, serving=true, terminating=true`. Смысл: новых соединений сюда больше не направляют, но под ещё жив и доигрывает уже принятые запросы. Это и есть механизм graceful shutdown на уровне сервиса.
- Перевод в это состояние произошёл **в ту же секунду**, что и команда удаления, — то есть за 15 секунд до фактической смерти контейнера. Балансировщик узнаёт об уходе пода **раньше**, чем под перестаёт работать; именно этот запас и обеспечивает раскатку без потерь.
- Новый под появляется в слайсе **сразу**, ещё не будучи готовым (`ready=false`), и переключается в `true` только после успешной readiness-пробы.
- Старый (`.87`) и новый (`.88`) адреса какое-то время сосуществуют в слайсе — состав эндпоинтов в момент churn'а временно **больше**, чем `replicas`.

## C. Провал readiness: эндпоинт уходит без удаления пода

Удаляем `index.html` — nginx начинает отдавать `403`, readiness падает:

```bash
kubectl exec svc-demo-779979d447-r9l58 -- rm /usr/share/nginx/html/index.html
# через 15 с возвращаем файл обратно
```

```
18:42:48 | ADDR                      READY        SERVING      TERM
18:42:48 | 10.244.0.86,10.244.0.88   true,true    true,true    false,false
>>> 18:42:51 rm index.html -> nginx отдаёт 403
18:43:01 | 10.244.0.86,10.244.0.88   true,false   true,false   false,false
>>> 18:43:07 возвращаем index.html
18:43:07 | 10.244.0.86,10.244.0.88   true,true    true,true    false,false
```

```
>>> под всё это время:
svc-demo-779979d447-r9l58   1/1   Running   0
```

Как то же самое выглядит в классическом объекте `Endpoints`:

```bash
kubectl get endpoints svc-demo-svc
kubectl get endpoints svc-demo-svc -o yaml
```

```
NAME           ENDPOINTS         AGE
svc-demo-svc   10.244.0.86:80    9m41s        <- в списке остался один адрес

subsets:
- addresses:
  - ip: 10.244.0.86
    targetRef:
      kind: Pod
      name: svc-demo-779979d447-shgdw
  notReadyAddresses:                          <- выбывший адрес не исчез, а переехал сюда
  - ip: 10.244.0.88
    targetRef:
      kind: Pod
      name: svc-demo-779979d447-r9l58
  ports:
  - name: http
    port: 80
    protocol: TCP
```

**Наблюдения:**
- Отличие от сценария B принципиальное: `terminating` остался `false`, а `serving` стал `false`. То есть под **не завершается — он просто не готов**. Kubernetes не убивает его и не создаёт замену (см. миссию 6).
- В `EndpointSlice` адрес остаётся в списке с флагами `false`; в старом `Endpoints` он переезжает из `addresses` в **`notReadyAddresses`**. Поэтому в выводе `kubectl get endpoints` он «пропадает» — но объект о нём помнит, и это удобно для диагностики: сразу видно, какой именно под выпал и почему.
- Возврат занял **один цикл пробы** (18:43:07, ровно в момент восстановления файла): эндпоинт вернулся, никаких рестартов.
- Реакция на поломку заняла ~10 c (18:42:51 → 18:43:01) — это `periodSeconds=3 × failureThreshold=3`.

## D. Rolling update: полная ротация эндпоинтов под нагрузкой

Одновременно: смена образа, watch эндпоинтов и непрерывный поток из 90 запросов.

```bash
kubectl set image deploy/svc-demo nginx=nginx:1.28
kubectl exec client -- sh -c 'ok=0; fail=0; i=0; while [ $i -lt 90 ]; do
  if wget -T 2 -qO- http://svc-demo-svc:8080/ >/dev/null 2>&1; then ok=$((ok+1)); else fail=$((fail+1)); fi
  i=$((i+1)); done; echo "OK=$ok FAIL=$fail"'
```

```
IP до:  svc-demo-779979d447-r9l58 10.244.0.88
        svc-demo-779979d447-shgdw 10.244.0.86

>>> 18:44:05 старт rolling update
OK=90 FAIL=0
deployment "svc-demo" successfully rolled out

18:44:03 | svc-demo-svc   10.244.0.86:80,10.244.0.88:80                  9m58s
18:44:07 | svc-demo-svc   10.244.0.86:80,10.244.0.88:80                  10m
18:44:07 | svc-demo-svc   10.244.0.86:80,10.244.0.88:80,10.244.0.89:80   10m    <- +новый
18:44:08 | svc-demo-svc   10.244.0.86:80,10.244.0.89:80                  10m    <- −старый .88
18:44:10 | svc-demo-svc   10.244.0.86:80,10.244.0.89:80                  10m
18:44:11 | svc-demo-svc   10.244.0.89:80,10.244.0.90:80                  10m    <- +.90, −.86

IP после: svc-demo-685ff56b56-tgv6g 10.244.0.89
          svc-demo-685ff56b56-xmtdp 10.244.0.90
```

**Наблюдения:**
- Состав эндпоинтов **полностью обновился** (`.86,.88` → `.89,.90`) за ~6 секунд, и всё это время в списке было **не меньше двух** адресов.
- Порядок всегда один: **сначала добавляется новый** адрес, потом убирается старый. Это следствие `maxUnavailable=0` (для 2 реплик от 25%) — Deployment не имеет права убрать старый под, пока новый не стал `Ready`, а контроллер эндпоинтов сразу отражает это в списке.
- **`OK=90 FAIL=0`** — ни один запрос не потерян при полной смене всех бэкендов. Работает связка из трёх механизмов: readiness не пускает в трафик неготовый под, эндпоинт уходит из балансировки в момент начала остановки, а `preStop` даёт поду доработать принятые соединения.

## E. Масштабирование в ноль: эндпоинты исчезают полностью

```bash
kubectl scale deploy/svc-demo --replicas=0     # затем обратно на 2
```

```
18:44:41 | svc-demo-svc   10.244.0.89:80,10.244.0.90:80   10m
>>> 18:44:43 scale -> 0
18:44:44 | svc-demo-svc   <none>                          10m        <- через 1 секунду

>>> 18:45:06 запрос к сервису без эндпоинтов:
wget: can't connect to remote host (10.105.131.225): Connection refused
не отвечает (exit=1)

>>> 18:45:07 scale -> 2
18:45:10 | svc-demo-svc                                   11m
18:45:10 | svc-demo-svc   10.244.0.91:80                  11m
18:45:10 | svc-demo-svc   10.244.0.91:80,10.244.0.92:80   11m

>>> итог:
      5 I am svc-demo-685ff56b56-hk8fk
      1 I am svc-demo-685ff56b56-t7hbr
```

**Наблюдения:**
- Список опустел **через 1 секунду** после команды, хотя сами поды из-за `preStop` жили ещё 15 секунд. Ещё одно подтверждение: удаление эндпоинта — это **начало** остановки пода, а не её конец.
- Сервис при этом никуда не делся: объект жив, ClusterIP тот же, DNS-имя резолвится. Отвечает `Connection refused` — ровно та же картина, что у сервиса с несовпадающим селектором (миссия 7, сценарий G). По ответу эти две ситуации неразличимы, различает их только `kubectl get endpoints`.
- Восстановление заняло ~3 секунды и прошло теми же ступенями: пустой список → 1 адрес → 2 адреса. Новые поды получили **новые IP** (`.91`, `.92`) — адреса подов не переиспользуются, и это ещё одна причина, по которой обращаться к подам напрямую по IP нельзя.

## Сводка: что и как быстро меняет состав эндпоинтов

| Событие | Реакция эндпоинтов | Задержка | Промежуточное состояние |
|---|---|---|---|
| Появился новый под | адрес заводится сразу с `ready=false`, затем `true` | по готовности пробы | `ready=false, serving=false` |
| Под стал `Ready` | адрес начинает принимать трафик | ~1 c | — |
| Под помечен на удаление | `ready=false, serving=true, terminating=true` | **та же секунда** | держится весь grace period |
| Под фактически умер | адрес удаляется из слайса | после `preStop` + SIGTERM | — |
| Провал readiness | адрес → `notReadyAddresses` | `period × failureThreshold` | `ready=false, serving=false, terminating=false` |
| Восстановление readiness | адрес возвращается | один успешный цикл пробы | — |
| `scale` вверх | адреса добавляются по мере готовности | секунды | — |
| `scale` вниз / в 0 | адреса убираются | **~1 c**, до смерти подов | — |
| Rolling update | полная ротация, «сначала +новый, потом −старый» | ~6 c на 2 реплики | список временно длиннее `replicas` |

## Выводы

1. **Эндпоинты — это не конфигурация, а непрерывно пересчитываемое состояние.** Объект переписывается при каждом изменении в подах; за одно масштабирование прошло 5 обновлений подряд. Руками список эндпоинтов не ведут — им управляет контроллер, а единственный рычаг влияния — лейблы и готовность подов.
2. **Удаление эндпоинта опережает смерть пода.** И при `delete pod`, и при `scale --replicas=0` адрес выбывал из балансировки **в ту же секунду**, а сам под жил ещё 15 секунд (`preStop`). Этот зазор и есть окно graceful shutdown: балансировщик перестаёт слать новое, под доигрывает старое.
3. **Состояние эндпоинта трёхзначное, а не двоичное.** `ready` (пускать ли новые соединения), `serving` (обслуживает ли фактически) и `terminating` (завершается ли) различают две принципиально разные ситуации: «под не готов, но живёт» (C) и «под готов, но уходит» (B). В старом объекте `Endpoints` этой детализации нет — там только `addresses` / `notReadyAddresses`.
4. **Полная ротация бэкендов проходит без потери запросов** — `OK=90 FAIL=0` при смене обоих подов (D). Это результат не одного механизма, а трёх сразу: readiness-гейт на входе, раннее снятие эндпоинта на выходе и `preStop`-задержка. Уберите любой — и появятся `FAIL`.
5. **Порядок при rolling update: сначала добавить, потом убрать.** При `maxUnavailable=0` список эндпоинтов ни на мгновение не проседает ниже рабочего размера, а в момент churn'а даже превышает `replicas`.
6. **Пустой список эндпоинтов внешне неотличим от неправильного селектора** — в обоих случаях `Connection refused` при живом ClusterIP и работающем DNS. Диагностика всегда начинается с `kubectl get endpoints`, а не с `kubectl get svc`.
7. **IP подов после пересоздания не переиспользуются** (`.89/.90` → `.91/.92`), поэтому любое обращение к подам в обход сервиса — по зафиксированному IP — обречено.
