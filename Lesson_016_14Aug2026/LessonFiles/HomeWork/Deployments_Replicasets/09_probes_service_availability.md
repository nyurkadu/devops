# 9. Влияние проб контейнера на доступность подов через сервис

Задание: **Исследовать влияние проб контейнера на доступность подов через сервис.**

## Метод измерения

В миссиях 6 и 8 провал пробы наблюдался «изнутри кластера» — по статусам и эндпоинтам. Здесь нужен взгляд **со стороны клиента**: сколько запросов реально получит ошибку. Поэтому стенд построен на одном принципе:

> **readiness-проба проверяет ровно тот же путь `/`, который запрашивают клиенты.**

Это принципиально. Если проба смотрит на отдельный служебный URL, то «поломка» видна только ей, а клиент продолжает получать корректные ответы — измерить ущерб невозможно. Когда пути совпадают, удаление `index.html` делает под одинаково сломанным и для пробы (`403` → readiness падает), и для пользователя (`403` → запрос неуспешен). Разница между этими двумя моментами и есть **окно, в течение которого сервис раздаёт ошибки**.

Нагрузка подаётся из пода-клиента непрерывным потоком с отметкой времени по каждому запросу:

```bash
kubectl exec client -- sh -c 'i=0; while [ $i -lt 120 ]; do
  r=$(wget -T 2 -qO- http://probe-svc-svc:80/ 2>/dev/null)
  if [ -n "$r" ]; then echo "$(date +%T) OK $r"; else echo "$(date +%T) FAIL"; fi
  i=$((i+1)); sleep 0.25; done' > load.log
```

Каждый под отдаёт своё имя, поэтому из лога видно не только число ошибок, но и **кто именно** обслужил каждый запрос.

> Время в логах клиента — **UTC** (busybox внутри пода), время в командах хоста — **+03:00**. В отчёте это разведено явно.

Файл [09_probe-svc.yaml](09_probe-svc.yaml):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: probe-svc
  labels:
    app: probe-svc
spec:
  replicas: 3
  selector:
    matchLabels:
      app: probe-svc
  template:
    metadata:
      labels:
        app: probe-svc
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          command:
            - /bin/sh
            - -c
            - >
              echo "I am $HOSTNAME" > /usr/share/nginx/html/index.html &&
              echo ok > /usr/share/nginx/html/live &&
              echo ok > /usr/share/nginx/html/startup &&
              exec nginx -g 'daemon off;'
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
          startupProbe:
            httpGet:
              path: /startup
              port: 80
            periodSeconds: 2
            failureThreshold: 15
          livenessProbe:
            httpGet:
              path: /live
              port: 80
            periodSeconds: 5
            failureThreshold: 3
          # ВАЖНО: readiness проверяет тот же путь "/", который запрашивают клиенты.
          # Значит "сломанный под" одинаково виден и пробе, и пользователю —
          # можно измерить, сколько запросов получит ошибку до вывода пода из сервиса.
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 2
            failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: probe-svc-svc
spec:
  selector:
    app: probe-svc
  ports:
    - port: 80
      targetPort: 80
```

Базовый замер — 45 запросов, все успешны, нагрузка равномерна:

```

     14 I am probe-svc-7d6cf64f9f-qsn2v

```

## Опыт 1: чуткая readiness (`period=2, failureThreshold=2`)

Под нагрузкой ломаем один под из трёх:

```bash
kubectl exec probe-svc-7d6cf64f9f-rvxz9 -- rm /usr/share/nginx/html/index.html
# через 20 с возвращаем файл
```

Хронология (время клиента, UTC; поломка в 15:55:38):

```
15:55:37 OK   probe-svc-7d6cf64f9f-rvxz9
15:55:37 OK   probe-svc-7d6cf64f9f-qsn2v
15:55:38 OK   probe-svc-7d6cf64f9f-rvxz9      <- последний успешный ответ сломанного пода
15:55:38 OK   probe-svc-7d6cf64f9f-qsn2v
15:55:38 FAIL                                 <- единственная ошибка
15:55:38 OK   probe-svc-7d6cf64f9f-qsn2v
15:55:39 OK   probe-svc-7d6cf64f9f-qsn2v
15:55:39 OK   probe-svc-7d6cf64f9f-gmbrb      <- дальше отвечают только два здоровых пода
15:55:40 OK   probe-svc-7d6cf64f9f-gmbrb
...
```

Возврат после починки (файл вернули в 15:55:58):

```
15:56:00 OK   probe-svc-7d6cf64f9f-gmbrb
15:56:01 OK   probe-svc-7d6cf64f9f-rvxz9      <- под снова в строю через ~3 с
15:56:01 OK   probe-svc-7d6cf64f9f-qsn2v
```

Итог за весь прогон:

```
      1 FAIL
     48 probe-svc-7d6cf64f9f-gmbrb
     53 probe-svc-7d6cf64f9f-qsn2v
     18 probe-svc-7d6cf64f9f-rvxz9
всего: 120
```

**Наблюдения:**
- Из 120 запросов ошибку получил **ровно один** — тот, что успел попасть на сломанный под в промежутке между поломкой и её обнаружением.
- Сломанный под исчез из ротации в ту же секунду: после `15:55:38` его ответов нет вплоть до восстановления. Проба сработала быстрее теоретического максимума (`period × failureThreshold = 4 c`), потому что очередной цикл пробы пришёлся почти сразу на поломку.
- Сервис **остался доступен**: 119 из 120 запросов обслужены. Но обслужены двумя подами вместо трёх — доступность сохранена ценой **потери трети мощности**, о чём ни `kubectl get svc`, ни сервис никак не сигнализируют.
- Возврат в ротацию занял ~3 с после починки и обошёлся без единой ошибки.

## Опыт 2: та же поломка, «расслабленная» readiness (`period=10, failureThreshold=3`)

Меняем **только тайминги пробы**, всё остальное — идентично:

```bash
kubectl patch deploy probe-svc --type=json -p='[
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/periodSeconds","value":10},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/failureThreshold","value":3}
]'
```

```
UTC поломки: 15:57:08

=== итог ===
     29 FAIL
      8 probe-svc-84f8b854d9-bnpzg
     51 probe-svc-84f8b854d9-lcmkd
     72 probe-svc-84f8b854d9-nmcn9
всего: 160

=== первый и последний FAIL ===
15:57:08 FAIL
15:57:30 FAIL
```

**Наблюдения:**
- **29 ошибок вместо 1** при абсолютно той же поломке. Единственное отличие — параметры пробы.
- Окно раздачи ошибок: `15:57:08 → 15:57:30` = **22 секунды** (теоретический максимум `10 × 3 = 30 c`).
- Доля потерь — 18% всех запросов за прогон; в пересчёте на трафик сломанного пода это **все** его запросы в течение 22 секунд.
- Вывод для эксплуатации: `periodSeconds` и `failureThreshold` readiness — это **прямой множитель количества ошибок**, которые увидят пользователи при отказе одного пода. Осторожничать с ними «чтобы не флапало» = сознательно продлевать инцидент.

## Опыт 3: readiness-пробы нет вовсе

```bash
kubectl patch deploy probe-svc --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/readinessProbe"}]'
kubectl exec probe-svc-74f9c9885-2bb26 -- rm /usr/share/nginx/html/index.html
```

Через 25 секунд после поломки:

```
=== под и эндпоинты ===
probe-svc-74f9c9885-2bb26   1/1   Running   0                        <- "здоров"
probe-svc-svc   10.244.0.101:80,10.244.0.102:80,10.244.0.103:80      <- все три в сервисе

=== 90 запросов ===
     27 FAIL
     38 I am probe-svc-74f9c9885-7blzl
     25 I am probe-svc-74f9c9885-hxqtx
```

**Наблюдения:**
- **30% запросов падают, и это навсегда** — само не починится. Сломанный под остаётся `1/1 Running`, числится в Endpoints и продолжает получать свою треть трафика.
- Без readiness Kubernetes считает готовым любой запущенный контейнер. Единственный критерий — «процесс стартовал», а не «приложение работает».
- Мониторинг на уровне Kubernetes при этом **полностью зелёный**: `3/3 READY`, `AVAILABLE 3`, эндпоинтов три. Отказ виден только клиентам.

### Сравнение трёх конфигураций на одной и той же поломке

| Конфигурация readiness | Окно ошибок | Ошибок клиента | Комментарий |
|---|---|---|---|
| `period=2, failure=2` | ~1 c | **1 из 120** (0.8%) | под выведен почти мгновенно |
| `period=10, failure=3` | 22 c | **29 из 160** (18%) | те же 22 секунды инцидента |
| пробы нет | ∞ | **27 из 90** (30%) | не восстановится само |

## Опыт 4: влияние liveness — перезапуск под нагрузкой

Ломаем **только** liveness (`/live`), пользовательская страница `/` остаётся рабочей:

```bash
kubectl exec probe-svc-7d6cf64f9f-59dfd -- rm /usr/share/nginx/html/live
```

```
=== итог ===
     42 probe-svc-7d6cf64f9f-59dfd
     50 probe-svc-7d6cf64f9f-5ppbx
     48 probe-svc-7d6cf64f9f-d2vcp
всего: 140     FAIL: 0
```

Но в ответах перезапущенного пода есть **разрыв**:

```
15:59:44 x3
15:59:45 x1
15:59:46 x1        <- последний ответ перед рестартом
                   <- ~4 секунды пода нет в ротации
15:59:50 x3        <- вернулся
15:59:52 x2
```

```
Events:
  Warning  Unhealthy  33s (x3 over 43s)  kubelet   Liveness probe failed: HTTP probe failed with statuscode: 404
  Normal   Killing    33s                kubelet   Container nginx failed liveness probe, will be restarted

probe-svc-7d6cf64f9f-59dfd   1/1   Running   1        <- RESTARTS=1
```

**Наблюдения:**
- **Ни одной ошибки у клиента**, хотя контейнер был убит и поднят заново. Как только контейнер перешёл в состояние Terminated, статус пода стал `NotReady`, и эндпоинт ушёл из балансировки **раньше**, чем клиент успел попасть на мёртвый порт.
- Цена перезапуска — не ошибки, а **~4 секунды работы на 2/3 мощности**. Под нагрузкой, близкой к пределу, эта «дыра» превращается уже в реальные таймауты у пользователей.
- Здесь сработала связка: liveness перезапустила контейнер, а **readiness прикрыла окно перезапуска**. Если бы readiness не было (опыт 3), каждый рестарт liveness превращался бы в порцию `connection refused`.

## Опыт 5: влияние startup-пробы на доступность сервиса

Выкатываем новую ревизию с заведомо провальной startup-пробой и меряем трафик во время застрявшей раскатки:

```bash
kubectl patch deploy probe-svc --type=json -p='[
  {"op":"add","path":"/spec/progressDeadlineSeconds","value":60},
  {"op":"replace","path":"/spec/template/spec/containers/0/startupProbe/httpGet/path","value":"/no-such-startup"},
  {"op":"replace","path":"/spec/template/spec/containers/0/startupProbe/failureThreshold","value":5}
]'
```

```
=== поды в момент застрявшей раскатки ===
probe-svc-7d6cf64f9f-59dfd   1/1   Running   1        <- старая ревизия
probe-svc-7d6cf64f9f-5ppbx   1/1   Running   0
probe-svc-7d6cf64f9f-d2vcp   1/1   Running   0
probe-svc-b6f497b5b-n2q2p    0/1   Running   2        <- новый под, startup не проходит

=== эндпоинты ===
probe-svc-svc   10.244.0.104:80,10.244.0.105:80,10.244.0.106:80    <- только старые три

=== трафик за это время (100 запросов) ===
     39 I am probe-svc-7d6cf64f9f-59dfd
     35 I am probe-svc-7d6cf64f9f-5ppbx
     26 I am probe-svc-7d6cf64f9f-d2vcp

=== состояние деплоймента ===
probe-svc   3/3   1     3
Conditions:
  Available      True    MinimumReplicasAvailable
  Progressing    True    ReplicaSetUpdated
```

**Наблюдения:**
- **100 запросов, 0 ошибок** — все обслужены тремя подами старой ревизии. Битый под в сервис не попал ни на секунду.
- Под с непройденной startup-пробой — это `0/1`, а `0/1` для сервиса не существует. Startup-проба работает как **карантин на входе**: пока приложение не подтвердило, что стартовало, трафика оно не увидит.
- Так readiness/startup + `maxUnavailable=0` образуют защиту от выкатки: сломанная версия не может отобрать трафик у работающей.

## Сводка: как каждая проба влияет на доступность через сервис

| Проба | Механизм влияния | Что видит клиент при отказе | Цена ошибки в конфигурации |
|---|---|---|---|
| `readinessProbe` | включает/исключает под из Endpoints | ошибки **только** в окне обнаружения (`period × failureThreshold`) | **прямой множитель** числа ошибок: 1 → 29 → 27 навсегда |
| `livenessProbe` | перезапускает контейнер | ошибок нет (закрывает readiness), но провал в мощности на время рестарта | частые рестарты = хроническая нехватка реплик |
| `startupProbe` | не пускает под в сервис до подтверждения старта | ничего — битый под просто не получает трафик | слишком короткая → медленный старт примут за отказ |

## Выводы

1. **Доступность через сервис определяет readiness — и только она.** Liveness и startup влияют на трафик косвенно, через тот же механизм: меняют готовность пода, а уже она — состав Endpoints.
2. **Тайминги readiness — это напрямую количество ошибок у пользователей.** Один и тот же отказ дал 1 ошибку при `period=2, failure=2` и 29 при `period=10, failure=3`. «Помягче, чтобы не флапало» означает «дольше отдавать ошибки».
3. **Без readiness-пробы отказ не лечится вообще:** сломанный под остаётся в ротации навсегда и стабильно забирает свою долю трафика (30%), а Kubernetes при этом рапортует `3/3 READY`. Отсутствие readiness — не «нейтральная» настройка, а гарантированный тихий отказ.
4. **Readiness делает отказ мягким, но не бесплатным:** сервис продолжает работать, однако на меньшем числе реплик. Доступность и мощность — разные вещи, и сервис сигнализирует только о первой.
5. **Liveness без readiness опасна:** сама по себе она даёт окно `connection refused` на каждый рестарт. В опыте 4 ошибок не было именно потому, что readiness успевала снять эндпоинт до того, как клиент попадал на мёртвый контейнер.
6. **Startup-проба — карантин на входе:** под, не прошедший её, для сервиса не существует, поэтому сломанная новая ревизия не может отобрать трафик у работающей (0 ошибок за всю застрявшую раскатку).
7. **Практический вывод по настройке:** readiness должна проверять **тот же путь и ту же логику, что и боевой трафик** (иначе она «зелёная» на сломанном приложении), и быть настроена чутко — короткий `periodSeconds`, малый `failureThreshold`. Liveness, наоборот, должна быть грубой и терпеливой: её задача — вытащить процесс из зависания, а не реагировать на каждую флуктуацию.
