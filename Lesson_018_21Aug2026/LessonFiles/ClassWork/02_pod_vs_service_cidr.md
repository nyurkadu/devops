# Адресация в Kubernetes: pod CIDR и service CIDR

В кластере одновременно работают **две разные адресные сети**, и устроены они принципиально
по-разному. Именно здесь чаще всего возникает путаница, поэтому разберём каждую отдельно,
а потом посмотрим, как они работают в паре.

---

## 1. Pod CIDR — настоящая сеть

Пример из нашего кластера: `10.244.0.0/16`.

* Адреса раздаёт **CNI-плагин** (у нас Calico IPAM), а не сам Kubernetes.
* Адрес получает **под**, и это реальный адрес на реальном интерфейсе — `eth0` внутри пода,
  `veth`-пара на ноде, запись в таблице маршрутизации.
* Он **пингуется**, виден в `tcpdump`, по нему ходят настоящие пакеты.
* Он **эфемерный**: пересоздал под — получил другой IP. Поэтому на pod IP нельзя опираться
  в конфигурации приложений.
* Calico дополнительно режет этот диапазон на блоки `/26` и закрепляет за нодами:

```
10.244.15.192/26   → нода calico
10.244.228.0/26    → нода calico-m02
```

Смысл блоков — **не согласовывать каждый адрес глобально**. Нода владеет своим блоком,
раздаёт из него локально, а остальным нодам объявляет по BGP один короткий маршрут вместо
сотни. Отсюда же строка `blackhole` в таблице маршрутов: пакеты на ещё не выданные адреса
своего блока отбрасываются сразу, а не бродят по сети.

---

## 2. Service CIDR — не сеть, а таблица правил

Пример из нашего кластера: `10.96.0.0/12`.

* Адрес выдаёт **API-сервер** из диапазона `--service-cluster-ip-range`.
* Адрес получает **Service**, и вот главное: **этого адреса физически не существует**.
  Ни один сетевой интерфейс в кластере не имеет адрес `10.96.171.115`. Нет ARP, нет маршрута,
  отвечать нечему.
* ClusterIP — это по сути **ключ поиска в правилах iptables/IPVS**, которые kube-proxy разложил
  на каждой ноде. Пакет уходит на `10.96.x.x` → ядро ноды ещё до маршрутизации делает DNAT,
  подменяя получателя на реальный pod IP → дальше пакет едет уже по pod CIDR.
* Адрес **стабилен** всё время жизни Service — поэтому именно на него указывает DNS-запись
  CoreDNS (`web.default.svc.cluster.local`).

### Следствия, которые сбивают с толку

* `ping ClusterIP` молчит — правила написаны под TCP/UDP на конкретный порт, ICMP там просто нет;
* в `tcpdump` этот адрес не видно дальше первого хопа — он уже переписан;
* адрес не «принадлежит» ноде, поэтому не конфликтует и не требует ARP.

## 3. Сравнительная таблица

| Признак                   | Pod CIDR                              | Service CIDR                            |
| ------------------------- | ------------------------------------- | --------------------------------------- |
| Пример из нашего кластера | `10.244.0.0/16`                       | `10.96.0.0/12`                          |
| Кто раздаёт адреса        | **CNI-плагин** (Calico IPAM)          | **API-сервер**                          |
| Что получает адрес        | под                                   | Service                                 |
| Есть ли сетевой интерфейс | да, `eth0` внутри пода                | **нет**, интерфейса не существует       |
| Где «живёт» адрес         | на ноде, в виде veth и маршрутов      | в правилах iptables/IPVS на каждой ноде |
| Отвечает на ping          | да                                    | нет                                     |
| Стабильность              | меняется при каждом пересоздании пода | постоянный на всё время жизни Service   |
| Задаётся при старте       | `--pod-network-cidr` / `--cni`        | `--service-cluster-ip-range`            |
| Виден снаружи кластера    | нет                                   | нет                                     |

---

## 4. Как они работают в паре

```
под-клиент → DNS-имя (CoreDNS)
           → ClusterIP 10.96.x.x         ← service CIDR
           → правило kube-proxy: DNAT
           → pod IP 10.244.x.x           ← pod CIDR
           → маршрут Calico до нужной ноды
```

Service CIDR даёт **стабильную точку входа и балансировку**, pod CIDR — **реальную доставку
пакета**. Одно без другого не работает.

---

## 5. Как посмотреть у себя

```powershell
kubectl cluster-info dump | Select-String "cluster-cidr|service-cluster-ip-range" | Select-Object -First 2
kubectl get pods -o custom-columns=POD:.metadata.name,IP:.status.podIP
kubectl get svc  -o custom-columns=SVC:.metadata.name,CLUSTERIP:.spec.clusterIP
```

Проверьте по выводу: адреса подов начинаются с `10.244.`, адреса сервисов — с `10.96.`.
Диапазоны не пересекаются, и это обязательное требование.

---

## 6. Практическое следствие: не пересекайте диапазоны

Классическая авария при настройке — pod CIDR кластера пересекается с адресами офисной сети
или с VPC в облаке. Симптом коварный: часть внешних адресов из кластера недоступна, потому что
ядро считает их «своими» подами и не отправляет трафик наружу. Диагностируется долго, поэтому
диапазоны выбирают заранее и согласовывают с сетевиками.
