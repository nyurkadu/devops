# Теоретическая часть — разбор по пунктам

Разбор четырёх пунктов теории из [HOMEWORK.MD](HOMEWORK.MD). Практика — в [01_network_cni_calico.md](01_network_cni_calico.md), примеры оттуда используются здесь как иллюстрации.

Сквозная мысль всего занятия: **в Kubernetes сеть собрана из нескольких независимых слоёв, и каждый отвечает ровно за одну вещь**. Путаница начинается там, где слои смешивают. Поэтому дальше каждый слой разбирается отдельно, с ответом на вопрос «что сломается, если убрать именно его».

## 1. Сетевые концепции Kubernetes

### 1.1. Типы Services — зачем вообще нужен объект Service

Начнём с проблемы, которую он решает.

Под — сущность одноразовая. Он умирает при обновлении, при падении ноды, при масштабировании. При каждом рождении он получает **новый IP**. В нашей лаборатории это видно прямо: после `kubectl apply` реплики `web` получили `10.244.15.196` и `10.244.228.9`, а после пересоздания стали бы другими.

Значит, обращаться к поду по IP нельзя — адрес протухнет. Нужен **стабильный вход**, который сам знает актуальный список живых подов. Это и есть Service.

Service делает три вещи:

1. Даёт постоянный виртуальный адрес (ClusterIP) и постоянное DNS-имя.
2. Ведёт список живых подов по селектору меток (объект `EndpointSlice`).
3. Балансирует запросы между ними.

**Ключевой момент, который часто теряется:** Service — это не процесс и не прокси-сервер. Никто не «слушает» ClusterIP. Это просто запись в базе, которую kube-proxy превращает в правила фильтрации на каждой ноде. Подробнее в 1.2.

#### Типы Services

| Тип                          | Что даёт                                             | Кто видит                  | Когда применять                                             |
| ---------------------------- | ---------------------------------------------------- | -------------------------- | ----------------------------------------------------------- |
| `ClusterIP`                  | виртуальный IP из service CIDR                       | только изнутри кластера    | по умолчанию: связь между микросервисами                    |
| `NodePort`                   | порт (30000-32767) на **каждой** ноде                | снаружи, по `IP-ноды:порт` | быстрая проверка, dev-стенд, minikube                       |
| `LoadBalancer`               | внешний IP от облачного балансировщика               | из интернета               | продакшн в облаке (AKS, EKS, GKE)                           |
| `ExternalName`               | CNAME на внешнее DNS-имя, без IP и без проксирования | изнутри кластера           | «переезд»: имя внутри кластера → внешняя база данных        |
| headless (`clusterIP: None`) | адреса подов напрямую в DNS, без балансировки        | изнутри кластера           | StatefulSet, когда нужен конкретный экземпляр (базы, Kafka) |

Важная деталь: типы **вложены друг в друга**. `NodePort` — это ClusterIP плюс порт на нодах. `LoadBalancer` — это NodePort плюс внешний балансировщик. То есть создавая LoadBalancer, вы автоматически получаете и ClusterIP, и NodePort.

В minikube `LoadBalancer` вечно висит в `<pending>` — облачного провайдера, который выдал бы внешний IP, просто нет. Обходится через `minikube tunnel`.

#### Headless-сервис — зачем «сервис без сервиса»

Обычный ClusterIP скрывает поды: вы обращаетесь к одному адресу, а попадаете на случайный под. Для stateless-приложений это идеально, для баз данных — катастрофа: реплике нужно подключиться к **конкретному** мастеру, а не к «какому-нибудь узлу кластера».

`clusterIP: None` отключает балансировку: DNS-запрос возвращает не один виртуальный адрес, а список реальных IP всех подов. Плюс каждый под StatefulSet получает своё стабильное имя вида `db-0.db.default.svc.cluster.local`.

#### Проверка на нашем стенде

```powershell
kubectl get svc web -o wide
kubectl get endpointslices -l kubernetes.io/service-name=web
```

`EndpointSlice` — это и есть «список живых подов». Если под перестал быть `Ready`, он исчезает оттуда, и трафик на него больше не идёт. Отсюда практический вывод: **неправильно настроенный readiness-пробник ломает балансировку**, хотя сам под работает.

### 1.2. kube-proxy — как виртуальный адрес превращается в реальный

kube-proxy — компонент, который живёт на каждой ноде (в нашем кластере это поды `kube-proxy-*` в `kube-system`). Он следит за объектами Service и EndpointSlice в API и **программирует правила на ноде**.

Вопреки названию, современный kube-proxy почти ничего не проксирует. Он не пропускает трафик через себя — он лишь настраивает ядро Linux, а дальше пакеты идут без его участия. Поэтому, если kube-proxy упадёт, уже настроенные сервисы продолжат работать; сломается только реакция на изменения.

#### Три режима работы

| Режим       | Механизм                            | Особенности                                                  |
| ----------- | ----------------------------------- | ------------------------------------------------------------ |
| `userspace` | проксирование через процесс         | устарел, медленный, не используется                          |
| `iptables`  | цепочки правил NAT в ядре           | режим по умолчанию; выбор пода — через вероятностные правила |
| `ipvs`      | встроенный балансировщик ядра Linux | быстрее на больших кластерах, есть алгоритмы (rr, lc, sh)    |

Разница между `iptables` и `ipvs` проявляется на масштабе. В режиме iptables правила проверяются последовательно, и при тысячах сервисов таблица разрастается настолько, что каждое изменение пересчитывается заметное время. IPVS использует хеш-таблицу, поэтому не деградирует.

#### Что реально происходит с пакетом

Когда под `client` обращается к `http://web`:

1. **DNS**: имя `web.default.svc.cluster.local` резолвится в ClusterIP `10.96.171.115` (это CoreDNS, пункт 1.4).
2. Под отправляет пакет на `10.96.171.115:80`. Этого адреса **не существует** ни на одном интерфейсе.
3. Пакет попадает в цепочку `PREROUTING` таблицы `nat` ядра ноды, где kube-proxy заранее положил правило.
4. Правило делает **DNAT**: адрес назначения подменяется на IP одного из подов, например `10.244.15.196:80`. Выбор случайный, с равными вероятностями.
5. Дальше пакет обрабатывает **CNI** (Calico): смотрит маршрут, при необходимости заворачивает в IPIP-туннель на нужную ноду.
6. Ответ идёт обратно, ядро выполняет обратную трансляцию, и `client` видит ответ от `10.96.171.115` — как будто такой сервер и правда есть.

Отсюда важный вывод для отладки: **ping ClusterIP не работает и не должен**. Правила kube-proxy написаны для TCP/UDP на конкретных портах, ICMP они не обрабатывают. Живой сервис прекрасно отвечает на `curl` и молчит на `ping` — это нормально, а не поломка.

Посмотреть правила своими глазами:

```powershell
minikube ssh -p calico -- 'sudo iptables -t nat -L KUBE-SERVICES -n | head -20'
```

### 1.3. CNI и проверка подключения Calico

Подробный разбор — в [01_network_cni_calico.md](01_network_cni_calico.md). Здесь коротко о том, **какое место CNI занимает среди остальных слоёв**.

Kubernetes задаёт требования к сети, но не реализует их. Требования такие:

* каждый под получает уникальный IP;
* любой под общается с любым другим **без NAT**;
* нода видит все поды.

Реализация отдана наружу — плагину, соответствующему спецификации CNI. Kubelet при создании пода просто вызывает бинарь плагина и передаёт ему сетевой namespace контейнера.

Разделение обязанностей выглядит так:

| Слой         | Кто              | За что отвечает                                      |
| ------------ | ---------------- | ---------------------------------------------------- |
| адресация    | **CNI** (Calico) | выдать IP поду, создать интерфейс, построить маршрут |
| балансировка | **kube-proxy**   | превратить ClusterIP в IP конкретного пода           |
| имена        | **CoreDNS**      | превратить имя сервиса в ClusterIP                   |
| политики     | **CNI** (Calico) | применить или проигнорировать NetworkPolicy          |

Последняя строка — причина, по которой в задании отдельно требуется именно Calico. Объект `NetworkPolicy` создаёт API-сервер, но **применяет** его плагин. Плагины `bridge` и `kindnet` этого не умеют: политика спокойно создастся, а трафик пойдёт мимо неё. На практике это самая обидная ловушка — «политику написал, а она не работает», хотя сломан совсем другой слой.

Три уровня проверки, что Calico действительно подключен:

1. **Файлы на ноде** — `/etc/cni/net.d/10-calico.conflist` и бинари `/opt/cni/bin/calico`.
2. **Объекты Kubernetes** — DaemonSet `calico-node` на каждой ноде, CRD `*.crd.projectcalico.org`.
3. **Поведение** — трафик ходит между нодами, а `NetworkPolicy` реально его режет.

Первые два уровня доказывают установку, и только третий — что оно работает.

### 1.4. CoreDNS — телефонная книга кластера

CoreDNS — обычный под в `kube-system`, перед которым стоит сервис `kube-dns` с фиксированным адресом (обычно `10.96.0.10`). Этот адрес kubelet прописывает **в каждый создаваемый под**:

```powershell
kubectl exec client -- cat /etc/resolv.conf
```

```
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

Разберём все три строки — в них прячется большинство «странностей» DNS в Kubernetes.

**`nameserver`** — куда под шлёт DNS-запросы. Обратите внимание: это ClusterIP, то есть DNS работает поверх Service, а Service — поверх kube-proxy и CNI. Красивое следствие: если сломан CNI, то не работает и DNS, и диагностика упирается в «имена не резолвятся», хотя причина глубже.

**`search`** — список суффиксов, которые автоматически дописываются к коротким именам. Именно поэтому изнутри пода работает просто `http://web`: система последовательно пробует `web.default.svc.cluster.local`, `web.svc.cluster.local`, `web.cluster.local`.

**`ndots:5`** — самое неочевидное. Правило гласит: если в имени **меньше 5 точек**, сначала перебирать суффиксы из `search`, и только потом пробовать имя как есть. Для внутренних имён это удобно, но у внешних адресов вроде `api.github.com` (2 точки) получается 4 бесполезных запроса перед правильным. Отсюда типичный симптом «обращения наружу медленные». Лечится точкой в конце — `api.github.com.` означает «имя полное, ничего не дописывай».

#### Схема имён

Полное имя сервиса собирается так:

```
<сервис>.<namespace>.svc.cluster.local
```

Это прямо связано с пунктом про namespaces (4.6): обращение к `web` внутри своего namespace и к `web.production` — разные адреса. Namespace встроен в само имя, что и даёт логическое разделение.

Для headless-сервисов и StatefulSet добавляется ещё уровень: `<под>.<сервис>.<namespace>.svc.cluster.local`.

#### Как проверять

```powershell
kubectl exec dnsutils -- nslookup web.default.svc.cluster.local
kubectl -n kube-system get pods -l k8s-app=kube-dns
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=20
```

Практическая заметка из лабораторной: `nslookup` из образа busybox возвращает **код ошибки 1 даже при успешном резолве** — он не может обратно разрезолвить адрес самого DNS-сервера. Строки `Name:` и `Address:` при этом есть. Чтобы не гоняться за несуществующей проблемой, для проверок DNS лучше брать образ `agnhost`.

### 1.5. etcd — единственный источник правды

etcd — распределённое ключ-значение хранилище, в котором лежит **всё состояние кластера**: поды, сервисы, конфигмапы, секреты, роли, сетевые политики. Больше нигде состояние не хранится.

Это стоит осознать буквально: если удалить etcd, кластер исчезает целиком, даже если все ноды и контейнеры продолжают работать. И наоборот — имея бэкап etcd, можно восстановить кластер на чистом железе.

#### Кто с ним общается

Только **API-сервер**. Ни kubelet, ни планировщик, ни контроллеры, ни тем более пользователь не ходят в etcd напрямую. Это единственная точка входа, и именно там работают аутентификация, авторизация (RBAC), валидация и admission-контроллеры.

```
kubectl → API-сервер → etcd
                ↑
    kubelet, scheduler, controller-manager (через watch)
```

#### Механизм watch — почему кластер реагирует мгновенно

Компоненты не опрашивают API в цикле. Они открывают **watch** — долгоживущее соединение, по которому API-сервер сам присылает изменения. Поэтому цепочка «создали Deployment → появились поды» отрабатывает за доли секунды: контроллер получил событие, а не дождался очередного опроса.

Тот же механизм лежит в основе Calico: `calico-node` подписан на изменения `NetworkPolicy` и перестраивает правила фильтрации сразу после `kubectl apply`. В лабораторной это видно — доступ пропадает и возвращается мгновенно.

#### Кворум и почему нод управления нечётное число

etcd использует алгоритм консенсуса Raft: запись считается принятой, если её подтвердило **большинство** узлов. Отсюда правило нечётности:

| Узлов etcd | Кворум | Переживёт отказов |
| ---------- | ------ | ----------------- |
| 1          | 1      | 0                 |
| 3          | 2      | 1                 |
| 5          | 3      | 2                 |
| 4          | 3      | 1 (не лучше трёх) |

Четыре узла требуют кворума 3 и переживают всего один отказ — то же, что и три узла, но дороже. Поэтому в продакшне ставят 3 или 5.

В minikube etcd один, внутри пода `etcd-<нода>` на control-plane. Никакой отказоустойчивости, для учебного стенда это нормально.

#### Что важно помнить про секреты

Секреты в etcd по умолчанию хранятся **в base64, а не в шифрованном виде**. Это кодирование, а не защита. Кто получил доступ к файлам etcd или к бэкапу — получил все секреты. Отсюда две меры: шифрование на уровне API-сервера (`EncryptionConfiguration`) и вынос секретов во внешнее хранилище — следующий пункт.

### 1.6. Key Vault — секреты за пределами кластера

Key Vault (в Azure; аналоги — AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager) — внешнее защищённое хранилище паролей, ключей и сертификатов.

#### Зачем, если в Kubernetes уже есть Secrets

У встроенных секретов есть ограничения, которые в продакшне становятся неприемлемыми:

| Проблема Secret         | Что делает Key Vault                                      |
| ----------------------- | --------------------------------------------------------- |
| base64 — не шифрование  | хранит в зашифрованном виде, ключи в HSM                  |
| секрет лежит в кластере | секрета в кластере нет вовсе, он подтягивается по запросу |
| ротация вручную         | автоматическая ротация с версионированием                 |
| нет аудита обращений    | полный журнал: кто, когда и какой секрет читал            |
| секрет попадает в git   | в манифесте только ссылка на имя секрета, не значение     |
| у каждого кластера свой | один источник для всех кластеров и приложений             |

#### Как это подключается

Стандартный путь — **Secrets Store CSI Driver**: секрет монтируется в под как файл, а по желанию ещё и синхронизируется в обычный Kubernetes Secret для использования через `env`.

Схема получается такая:

```
Под → CSI-драйвер → Key Vault (аутентификация по managed identity ноды)
                       ↓
              секрет в виде файла в /mnt/secrets
```

Ключевая идея: приложение **не хранит пароль от хранилища паролей**. Аутентификация идёт через identity самой ноды или пода (Workload Identity), то есть облако само подтверждает «это действительно тот под, за кого себя выдаёт». Это снимает вечную проблему «а где хранить главный ключ».

Для нашей домашней работы Key Vault — теоретический пункт: в minikube облачного хранилища нет. Практическая часть про секреты (задание 2) делается на встроенных Secrets, и как раз поэтому важно понимать их ограничения.

## 2. Адресация: pod CIDR и service CIDR

Это пункт, где чаще всего возникает каша, поэтому разберём медленно.

В кластере одновременно живут **две независимые сети**, и их адреса нельзя путать.

### Сравнение

| Признак                   | Pod CIDR                              | Service CIDR                            |
| ------------------------- | ------------------------------------- | --------------------------------------- |
| Пример из нашего кластера | `10.244.0.0/16`                       | `10.96.0.0/12`                          |
| Кто раздаёт адреса        | **CNI-плагин** (Calico IPAM)          | **API-сервер**                          |
| Что получает адрес        | под                                   | Service                                 |
| Есть ли сетевой интерфейс | да, `eth0` внутри пода                | **нет**, интерфейса не существует       |
| Где «живёт» адрес         | на ноде, в виде veth и маршрутов      | в правилах iptables/IPVS на каждой ноде |
| Отвечает на ping          | да                                    | нет                                     |
| Стабильность              | меняется при каждом пересоздании пода | постоянный на всё время жизни Service   |
| Задаётся при старте       | `--pod-network-cidr` / `--cni`        | `--service-cluster-ip-range`            |
| Виден снаружи кластера    | нет                                   | нет                                     |

### Почему адрес сервиса «не существует»

Это главное, что нужно уложить в голове. ClusterIP — не адрес машины, а **ключ поиска в таблице правил**. Ни один сетевой интерфейс в кластере не имеет адреса `10.96.171.115`. Когда пакет уходит на этот адрес, ядро ноды ещё до маршрутизации подменяет получателя на реальный IP пода.

Отсюда всё остальное:

* `ping` ClusterIP молчит — правила написаны для TCP/UDP на конкретный порт;
* `tcpdump` на интерфейсе не покажет пакетов с этим адресом дальше первого хопа — он уже переписан;
* адрес не «принадлежит» ноде, поэтому не конфликтует и не требует ARP.

### Как посмотреть у себя

```powershell
kubectl cluster-info dump | Select-String "cluster-cidr|service-cluster-ip-range" | Select-Object -First 2
kubectl get pods -o custom-columns=POD:.metadata.name,IP:.status.podIP
kubectl get svc -o custom-columns=SVC:.metadata.name,CLUSTERIP:.spec.clusterIP
```

Проверьте по выводу: адреса подов начинаются с `10.244.`, адреса сервисов — с `10.96.`. Диапазоны не пересекаются, и это обязательное требование.

### Третий уровень: блоки IPAM

Calico дробит pod CIDR ещё раз — нарезает его на блоки `/26` (по 64 адреса) и закрепляет за нодами. В нашей лаборатории:

```
10.244.15.192/26   → нода calico
10.244.228.0/26    → нода calico-m02
```

Смысл в том, чтобы **не согласовывать каждый адрес глобально**. Нода владеет своим блоком и раздаёт из него локально, а остальным нодам объявляет по BGP один короткий маршрут вместо сотни. Это же объясняет строку `blackhole` в таблице маршрутов: пакеты на ещё не выданные адреса своего блока отбрасываются сразу, а не бродят по сети.

### Практическое следствие: не пересекайте диапазоны

Классическая авария при настройке: pod CIDR кластера пересекается с адресами офисной сети или с VPC в облаке. Симптом коварный — часть внешних адресов из кластера недоступна, потому что ядро считает их «своими» подами и не отправляет наружу. Поэтому диапазоны выбирают заранее и согласовывают с сетевиками.

## 3. Конфигурация и данные: env, ConfigMap, Secrets

### 3.1. Зачем это вообще нужно

Правило, из которого всё вытекает: **образ контейнера должен быть одинаковым для всех сред**. Один и тот же образ едет на dev, staging и prod, а различает их только конфигурация, поданная снаружи.

Если вшить адрес базы в образ, придётся собирать три разных образа, и тот, что тестировали, никогда не совпадёт с тем, что поедет в прод. Отсюда — вынос настроек в переменные окружения (подход «12-factor app»).

### 3.2. Три способа задать env

#### Способ 1: напрямую в манифесте

```yaml
env:
  - name: APP_PORT
    value: "8080"
  - name: LOG_LEVEL
    value: "debug"
```

Просто и наглядно. Подходит для значений, которые действительно принадлежат этому деплойменту и не меняются между средами. Минус: чтобы поменять значение, надо править и передеплоивать манифест.

Обратите внимание на кавычки у `"8080"` — значение переменной окружения всегда строка, и YAML требует явности, иначе получите ошибку типа.

#### Способ 2: из ConfigMap

Сначала создаём объект:

```powershell
kubectl create configmap app-config --from-literal=APP_PORT=8080 --from-literal=LOG_LEVEL=debug
```

Затем ссылаемся на него — по одному ключу:

```yaml
env:
  - name: APP_PORT
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: APP_PORT
```

или сразу все ключи целиком:

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

`envFrom` короче, но у него есть подвох: имена переменных берутся из ключей как есть, и если в ConfigMap окажется ключ с некорректным для переменной именем, он будет молча пропущен.

#### Способ 3: из Secret

Синтаксис такой же, меняется только тип ссылки:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: password
```

### 3.3. ConfigMap и Secret — в чём разница

| Признак               | ConfigMap                  | Secret                                                    |
| --------------------- | -------------------------- | --------------------------------------------------------- |
| Назначение            | обычные настройки          | пароли, токены, ключи, сертификаты                        |
| Хранение значения     | как есть, открытым текстом | base64 (**это кодирование, не шифрование**)               |
| В etcd                | открыто                    | открыто, если не включено шифрование at rest              |
| RBAC                  | обычные права              | обычно ограничивают отдельно                              |
| Вывод в `kubectl get` | значения видны             | значения скрыты за base64, но декодируются одной командой |
| Типы                  | один                       | несколько: `Opaque`, `dockerconfigjson`, `tls`, …         |
| Лимит размера         | 1 МБ                       | 1 МБ                                                      |

Про base64 стоит сказать прямо, потому что это источник ложного чувства безопасности:

```powershell
kubectl get secret db-secret -o jsonpath='{.data.password}'
```

Полученную строку раскодирует кто угодно за секунду. Secret отличается от ConfigMap не защитой содержимого, а тем, что к нему **принято** применять отдельные права доступа, шифрование хранилища и внешние хранилища (Key Vault из пункта 1.6).

### 3.4. Переменные или файлы — важное различие

И ConfigMap, и Secret можно подключить двумя способами, и разница между ними принципиальна.

| Способ                  | Как выглядит в контейнере | Обновляется при изменении объекта          |
| ----------------------- | ------------------------- | ------------------------------------------ |
| через `env` / `envFrom` | переменная окружения      | **нет** — только после перезапуска пода    |
| через `volumeMounts`    | файл в каталоге           | **да**, автоматически (с задержкой ~1 мин) |

Причина в устройстве Linux: окружение процесса формируется **в момент запуска** и не может быть изменено снаружи. Поэтому изменённый ConfigMap не долетит до уже работающего контейнера.

Это ловушка, на которую напарываются все: поправили ConfigMap, ждёте эффекта, а его нет. Правильный путь — перезапустить:

```powershell
kubectl rollout restart deployment/web
```

Если требуется подхват без перезапуска, монтируйте как файл:

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
containers:
  - name: app
    volumeMounts:
      - name: config
        mountPath: /etc/app
```

Тогда приложение должно само перечитывать файл — Kubernetes лишь обновит его содержимое.

### 3.5. Проверка на примере Go-приложения

Практический пункт задания (№2) удобно проверять минимальным приложением, которое просто печатает свои переменные:

```powershell
kubectl exec <под> -- printenv | Select-String "APP_|LOG_|DB_"
kubectl describe pod <под> | Select-String -Context 0,3 "Environment"
```

Порядок проверки, чтобы ничего не упустить:

1. переменная задана напрямую — видна в `printenv`;
2. переменная из ConfigMap — видна там же, значение совпадает с `kubectl get cm app-config -o yaml`;
3. переменная из Secret — видна в контейнере в открытом виде (внутри пода секрет уже расшифрован);
4. изменили ConfigMap → в поде значение **старое** → `rollout restart` → значение новое.

Четвёртый шаг стоит проделать сознательно: он лучше всего объясняет разницу между `env` и монтированием файлом.

## 4. Маршрутизация и безопасность

### 4.1. Ingress controller — обратный прокси на входе в кластер

Мы уже умеем попадать в кластер через `NodePort` и `LoadBalancer`, но у них есть общая беда: **один сервис — один порт или один внешний IP**. Для десяти приложений это десять балансировщиков, десять счетов от облака и десять сертификатов, которыми надо как-то управлять.

Ingress решает это иначе: один вход на весь кластер, а разбор запросов идёт **по HTTP-признакам** — по имени хоста и по пути URL.

#### Два разных объекта, которые путают

Это ровно тот случай, о котором в задании написано «Ingress vs ingress terms»:

| Термин                                    | Что это                                                                  | Кто создаёт                               |
| ----------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------- |
| **Ingress** (объект)                      | правило маршрутизации: хост, путь → сервис                               | вы, в YAML                                |
| **Ingress controller**                    | реальный прокси (nginx, Traefik, HAProxy), который эти правила исполняет | администратор кластера, ставится отдельно |
| **ingress** (со строчной, сетевой термин) | входящий трафик — направление, а не объект                               | —                                         |

Практическое следствие: **объект Ingress без установленного контроллера не делает ничего**. Он создастся, `kubectl get ingress` покажет его, поле ADDRESS останется пустым, и запросы никуда не пойдут. Это ровно та же логика, что с `NetworkPolicy` без Calico — объект есть, исполнителя нет.

В minikube контроллер включается аддоном:

```powershell
minikube addons enable ingress -p calico
kubectl -n ingress-nginx get pods
```

А слово «ingress» со строчной буквы в контексте NetworkPolicy (`policyTypes: [Ingress]`) означает совсем другое — направление трафика, входящий. Никакой связи с Ingress-контроллером там нет. Отсюда и путаница, вынесенная в задание отдельным пунктом.

#### Что умеет Ingress

* маршрутизация по хосту: `shop.example.com` → сервис `shop`, `api.example.com` → сервис `api`;
* маршрутизация по пути: `/api` → один сервис, `/` → другой;
* терминация TLS: сертификат лежит в Secret типа `tls`, наружу — HTTPS, внутрь — HTTP;
* базовые вещи прокси: редиректы, ограничение размера тела, таймауты, rate limit (через аннотации).

#### Gateway API — что идёт на смену

У Ingress есть врождённая проблема: всё, что выходит за рамки «хост + путь», делается через **аннотации**, и они у каждого контроллера свои. Манифест для nginx-ingress не переносится на Traefik.

Gateway API — новый стандарт, где эти возможности описаны типизированными объектами, а роли разделены:

| Объект         | Кто владеет             | Смысл                                   |
| -------------- | ----------------------- | --------------------------------------- |
| `GatewayClass` | администратор платформы | какая реализация используется           |
| `Gateway`      | администратор платформы | сам вход: порты, протоколы, сертификаты |
| `HTTPRoute`    | команда разработки      | правила маршрутизации своего приложения |

Разделение здесь не косметическое: команда разработки правит только свои маршруты и не может случайно сломать общий вход. У Ingress всё лежало в одном объекте, и разграничить права было невозможно.

### 4.2. Network Policy — файрвол внутри кластера

#### Проблема

По умолчанию сеть Kubernetes **полностью плоская**: любой под может обратиться к любому другому в любом namespace. Скомпрометировали один фронтенд — с него доступна и база, и сервис платежей, и админка.

NetworkPolicy — способ это ограничить, причём средствами Kubernetes, а не внешнего файрвола.

#### Модель, которую надо понять

Три правила, из которых следует всё остальное:

1. Пока на под **не наведена ни одна** политика — разрешено всё.
2. Как только появилась хотя бы одна политика с типом `Ingress` — весь входящий трафик к этому поду запрещён, кроме явно разрешённого.
3. Правил «запретить» не существует. Политики только **разрешают**; запрет получается отсутствием разрешений.

Третий пункт — самый непривычный. Нельзя написать «запретить доступ из namespace X». Можно только сказать «разрешено из A и B», и всё остальное отсечётся само.

Политики **складываются по OR**: если под попадает под три политики, разрешено объединение всех трёх правил. Порядок и приоритеты отсутствуют, в отличие от классических файрволов.

#### Разбор параметров

```yaml
spec:
  podSelector:            # 1. К КОМУ применяется политика
    matchLabels:
      app: web
  policyTypes:            # 2. КАКОЕ направление ограничиваем
    - Ingress
  ingress:
    - from:               # 3. КОМУ разрешаем
        - podSelector:
            matchLabels:
              role: client
      ports:              # 4. ЧТО разрешаем
        - protocol: TCP
          port: 80
```

| Поле               | Отвечает за       | Если пропустить                                |
| ------------------ | ----------------- | ---------------------------------------------- |
| `spec.podSelector` | защищаемые поды   | `{}` = все поды namespace                      |
| `policyTypes`      | направление       | выводится из наличия секций `ingress`/`egress` |
| `ingress.from`     | источники         | без `from` — разрешено отовсюду                |
| `ingress.ports`    | порты и протоколы | без `ports` — разрешены все порты              |

Отдельного внимания заслуживают три вида селекторов в `from`, потому что их легко перепутать:

| Селектор                                                    | Что выбирает                                |
| ----------------------------------------------------------- | ------------------------------------------- |
| `podSelector`                                               | поды **в том же** namespace, что и политика |
| `namespaceSelector`                                         | **все** поды в namespace с нужной меткой    |
| `namespaceSelector` + `podSelector` в одном элементе списка | только нужные поды в нужных namespace       |
| `ipBlock`                                                   | внешние адреса (для egress наружу)          |

Разница между «двумя селекторами в одном элементе» и «двумя элементами списка» — источник тонких ошибок:

```yaml
# И namespace, И под (логическое И)
from:
  - namespaceSelector: {matchLabels: {env: prod}}
    podSelector: {matchLabels: {app: front}}

# ИЛИ namespace, ИЛИ под (логическое ИЛИ) — обратите внимание на дефис
from:
  - namespaceSelector: {matchLabels: {env: prod}}
  - podSelector: {matchLabels: {app: front}}
```

Один дефис меняет смысл политики целиком.

#### Важные оговорки

* Политика работает **только если CNI её поддерживает** — см. пункт 1.3.
* Политики действуют в пределах своего namespace: `podSelector` не видит поды соседних namespace, для них нужен `namespaceSelector`.
* Не забывайте про DNS: если закрыли egress целиком, поды перестают резолвить имена. Нужно явно разрешить UDP/53 к `kube-system`.
* Политики оперируют метками, а не IP: адреса меняются при каждом пересоздании пода, а метки — нет.

### 4.3. Схема политик для классического веб-приложения

Возьмём типовую трёхуровневую архитектуру и распишем, какие политики нужны.

```
Интернет → [ingress-nginx] → [frontend] → [backend] → [database]
```

Принцип построения — **сверху вниз, от полного запрета**:

**Шаг 1. Запретить всё в namespace приложения.**

```yaml
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

После этого не работает вообще ничего, включая DNS. Это правильная отправная точка: дальше открываем только необходимое.

**Шаг 2. Разрешить DNS всем подам** — иначе не будет работать резолвинг имён:

```yaml
egress:
  - to:
      - namespaceSelector:
          matchLabels: {kubernetes.io/metadata.name: kube-system}
    ports:
      - {protocol: UDP, port: 53}
      - {protocol: TCP, port: 53}
```

**Шаг 3. Frontend принимает трафик только от Ingress-контроллера:**

```yaml
podSelector: {matchLabels: {tier: frontend}}
ingress:
  - from:
      - namespaceSelector:
          matchLabels: {kubernetes.io/metadata.name: ingress-nginx}
    ports: [{protocol: TCP, port: 8080}]
```

**Шаг 4. Backend принимает только от frontend:**

```yaml
podSelector: {matchLabels: {tier: backend}}
ingress:
  - from:
      - podSelector: {matchLabels: {tier: frontend}}
    ports: [{protocol: TCP, port: 8000}]
```

**Шаг 5. База принимает только от backend:**

```yaml
podSelector: {matchLabels: {tier: database}}
ingress:
  - from:
      - podSelector: {matchLabels: {tier: backend}}
    ports: [{protocol: TCP, port: 5432}]
```

Итоговая матрица доступа:

| Источник → Приёмник | frontend | backend | database |
| ------------------- | -------- | ------- | -------- |
| ingress-nginx       | ✅ :8080  | ❌       | ❌        |
| frontend            | —        | ✅ :8000 | ❌        |
| backend             | ❌        | —       | ✅ :5432  |
| любой другой под    | ❌        | ❌       | ❌        |

Что даёт эта схема: компрометация фронтенда не даёт доступа к базе — оттуда попросту нет сетевого пути. Это и есть смысл сегментации: ограничить не вход, а **боковое перемещение** внутри периметра.

### 4.4. Namespaces — логическое разделение

Namespace — способ разделить один физический кластер на логические части: команды, среды, приложения.

#### Что он разделяет, а что нет

| Разделяет                                      | **Не** разделяет                                |
| ---------------------------------------------- | ----------------------------------------------- |
| имена объектов (два `web` в разных namespace)  | сеть — по умолчанию все видят всех              |
| права доступа (RBAC привязывается к namespace) | ноды — поды соседей могут жить на той же ноде   |
| квоты ресурсов (`ResourceQuota`)               | версии API и CRD — они общие на кластер         |
| DNS-имена (`web.dev` vs `web.prod`)            | PersistentVolume — они не принадлежат namespace |

Строка про сеть — ключевая для домашней работы: **namespace сам по себе не даёт изоляции трафика**. Под из `dev` спокойно достучится до базы в `prod`, если не поставить NetworkPolicy. Именно поэтому задания 3 и 4 идут парой: сначала убеждаемся, что связь есть, потом ограничиваем её политиками.

#### Namespace в именах DNS

```
web                              → web в текущем namespace
web.production                   → web в namespace production
web.production.svc.cluster.local → полное имя
```

Обращение по короткому имени всегда идёт в свой namespace — на этом основано «одинаковые манифесты для dev и prod».

#### Что не лежит в namespace

Есть объекты уровня кластера: `Node`, `PersistentVolume`, `StorageClass`, `ClusterRole`, `CustomResourceDefinition`, сами `Namespace`. Проверить принадлежность:

```powershell
kubectl api-resources --namespaced=true  | Select-Object -First 15
kubectl api-resources --namespaced=false | Select-Object -First 15
```

#### Полезные команды

```powershell
kubectl create namespace dev
kubectl get pods -n dev
kubectl get pods --all-namespaces
kubectl config set-context --current --namespace=dev   # сменить namespace по умолчанию
```

Последняя команда экономит много времени: без неё придётся дописывать `-n dev` к каждой команде и рано или поздно забыть про него в самый неподходящий момент.

## Как всё связано — сводка

Разложим один HTTP-запрос из интернета до базы данных по слоям, каждый из которых разбирался выше:

| Шаг | Что происходит                                   | Отвечает              | Пункт |
| --- | ------------------------------------------------ | --------------------- | ----- |
| 1   | запрос приходит на внешний адрес                 | LoadBalancer          | 1.1   |
| 2   | по хосту и пути выбирается сервис                | Ingress controller    | 4.1   |
| 3   | имя сервиса превращается в ClusterIP             | CoreDNS               | 1.4   |
| 4   | ClusterIP подменяется на IP конкретного пода     | kube-proxy            | 1.2   |
| 5   | пакет доставляется на нужную ноду и в нужный под | CNI (Calico)          | 1.3   |
| 6   | проверяется, разрешён ли этот трафик             | NetworkPolicy → Felix | 4.2   |
| 7   | приложение читает настройки и пароль базы        | ConfigMap, Secret     | 3     |
| 8   | всё состояние объектов лежит в                   | etcd                  | 1.5   |

Если запрос не доходит — отлаживать имеет смысл именно по этим слоям, сверху вниз. Практически всегда проблема локализуется в одном из них, и знание границ ответственности экономит часы.
