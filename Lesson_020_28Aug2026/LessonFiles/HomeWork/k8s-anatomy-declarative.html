00

Почему манифест, а не командаЗапись плюс контроллер — и запись должна быть видна

Почти ни один объект Kubernetes не существует физически. Deployment, ReplicaSet, Service — это JSON-документы в базе etcd. Физически существуют только две вещи: процессы Linux на нодах и правила в ядре этих нод.

Между записью и реальностью стоит контроллер — программа, которая крутит бесконечный цикл: «прочитал желаемое состояние → посмотрел на фактическое → сделал разницу». Вся система построена на этом одном шаблоне, повторённом на каждом уровне.

Отсюда прямое следствие для практики. Если единственное, что вы отправляете в кластер, — это желаемое состояние, то и хранить надо именно его, а не последовательность команд, которая когда-то к нему привела. Императивная команда — это глагол: он выполнился и исчез. Манифест — существительное: оно лежит в файле и в git.

Императивно — глагол
kubectl create deployment shop --image=nginx:alpine --replicas=3

Что здесь сказано о пробах, лимитах, стратегии обновления? Ничего. Всё осталось на умолчаниях, и узнать, каких именно, можно только запросив объект обратно из кластера.

Декларативно — существительное
kubectl apply -f k8s-anatomy/30-deployment-shop.yaml

Всё, что попадёт в etcd, видно в файле целиком: replicas, strategy, resources, обе пробы. Файл лежит в git, его можно прочитать, отревьюить и применить повторно.

Три свойства, которых у команды нет в принципе

  • Идемпотентность. kubectl apply можно выполнить сто раз подряд — результат один и тот же. kubectl create на втором запуске упадёт с AlreadyExists.
  • Полнота. Манифест описывает объект целиком. Императивные флаги покрывают малую долю полей API: многоконтейнерный под, NetworkPolicy или ReplicaSet командой не создать вообще.
  • Обратимость. kubectl diff -f покажет разницу до применения, kubectl delete -f снесёт ровно то, что этот файл создал.
Что осталось императивным и почему

Команды наблюдения — kubectl get, describe, exec, logs, minikube ssh — манифестами не заменяются и не должны. Они ничего не меняют в кластере, а только показывают текущее состояние. Декларативность касается изменений, а не чтения.

Отдельный случай — kubectl patch --patch-file. Это тоже файл, но не полный манифест, а фрагмент. В лекции он используется дважды (31-, 32-), чтобы показать: масштабирование и смена образа — это правка одного поля, а не пересоздание объекта.

01

Подготовка средыDocker Desktop как фундамент

Мы используем minikube с драйвером docker. Это важный выбор: при таком драйвере нода кластера — это обычный контейнер Docker Desktop, в который можно зайти и увидеть процессы, cgroups и правила iptables своими глазами. С встроенным Kubernetes самого Docker Desktop так не получится — там поды живут в отдельном namespace containerd и в docker ps не видны.

Шаг 1 — сам кластер: манифестом не создаётся

Кластер существует до того, как появляется API, в который можно что-то отправить. Поэтому первые команды остаются императивными — иначе и быть не может.

PowerShellbootstrap
# Docker Desktop жив?

# поднимаем двухнодовый профиль с CNI, поддерживающим NetworkPolicy
# без --cni=calico по умолчанию встанет kindnet, а он политики НЕ исполняет
minikube start -p calico --cni=calico --nodes=2

# переключаем kubectl на этот кластер
kubectl config use-context calico

Шаг 2 — namespace: здесь начинается декларативность

Как только apiserver отвечает, всё дальнейшее описывается файлами. Первый из них — пространство имён, в котором будет жить вся лекция.

k8s-anatomy/00-namespace.yamlNamespace
# Namespace — не сеть и не машина, а всего лишь префикс в ключе,
# под которым объект лежит в etcd. Два объекта с одинаковым именем
# в разных namespace — это два РАЗНЫХ объекта.
apiVersion: v1
kind: Namespace
metadata:
  name: lab
  labels:
    # Метки на namespace — не украшение. NetworkPolicy умеет выбирать
    # namespace через namespaceSelector, и матчится он именно по ним.
    # Без метки правило «пропускать трафик из namespace lab» не написать.
    name: lab
    purpose: lecture-020
применитьkubectl apply -f k8s-anatomy/00-namespace.yaml kubectl config set-context --current --namespace=lab
было
kubectl create namespace lab
стало
kubectl apply -f k8s-anatomy/00-namespace.yaml

Вторая команда делает lab пространством имён по умолчанию — дальше можно не писать -n lab в каждой строке. В манифестах namespace всё равно указан явно: файл не должен зависеть от того, какой контекст сейчас активен.

Проверка манифестов до применения

kubectl apply --dry-run=client -f k8s-anatomy/ проверит синтаксис и схему всех файлов, ничего не создавая. kubectl diff -f <файл> покажет, что именно изменится в кластере, — незаменимо, когда применяете обновлённый манифест поверх работающего объекта.

Если что-то не поднимается

Проверьте, что Docker Desktop запущен и в его настройках выделено хотя бы 4 GB RAM. Для одноузлового варианта достаточно minikube start -p calico --cni=calico — все манифесты применятся и на одной ноде, просто раздел про размещение реплик будет менее наглядным.

02

Node — нодаЕдинственный объект, который нельзя описать манифестом

Нода — фундамент всей иерархии. Всё остальное в итоге сводится к тому, что на какой-то ноде запустился процесс. И это единственный объект лекции, для которого манифеста не существует и существовать не может.

Логически

Объект Node в etcd. Вы его не создаёте — kubelet при старте сам регистрируется в API и создаёт запись о себе.

В записи: сколько CPU и памяти доступно (capacity / allocatable), метки, taint-ы, условия здоровья (Ready, MemoryPressure). Планировщик читает именно эту запись, а не опрашивает железо.

Физически

Машина с Linux. В проде — сервер или VM. У нас — контейнер Docker Desktop с systemd внутри.

На ней обязательно крутятся три вещи: kubelet (агент, который создаёт контейнеры), kube-proxy (пишет правила в ядро) и container runtime (docker/containerd). Плюс CNI-плагин для сети подов.

Почему у ноды нет манифеста

Все прочие объекты работают по схеме «сначала запись, потом контроллер создаёт под неё реальность». Нода — наоборот: сначала существует машина, потом kubelet описывает её в etcd. Написать kind: Node и применить технически можно, но это создаст пустую карточку без машины — планировщик начнёт слать на неё поды, а исполнять их будет некому.

Единственное, что у ноды правят декларативно, — метки и taint-ы: kubectl label node, kubectl taint node или kubectl patch node. Само существование ноды кластеру не подвластно.

Почему на воркере процессов меньше

Это не сбой и не недонастроенная нода. Разница ровно в роли. Компоненты управляющего слоя описаны static-манифестами в /etc/kubernetes/manifests/ только на control-plane, и kubelet поднимает их лишь там. Воркер не участвует в принятии решений — он только исполняет поды, которые ему уже назначил планировщик.

Ключевая мысль

Нода — единственный объект Kubernetes, у которого запись в etcd описывает уже существующую физическую вещь. Все остальные объекты работают наоборот: сначала запись, потом контроллер создаёт под неё реальность. Именно поэтому у всех остальных есть манифест, а у ноды его нет.

03

Pod — подНе контейнер, а общий сетевой конверт

Под — минимальная единица, которую планировщик умеет размещать. Kubernetes никогда не планирует отдельный контейнер, только под целиком.

Логически

Объект Pod в etcd: список контейнеров, тома, запросы ресурсов. Плюс поле spec.nodeName — его заполняет планировщик.

Пока nodeName пустой, под находится в состоянии Pending и существует только как запись в базе. Никакого процесса ещё нет.

Физически

Группа процессов Linux на одной ноде, разделяющих сетевой namespace, IPC и (опционально) тома.

Первым runtime запускает крошечный pause-контейнер: он ничего не делает, но держит сетевой namespace. Все остальные контейнеры пода подключаются в namespace этого pause. Поэтому у пода один IP и контейнеры видят друг друга по localhost.

Манифест одноконтейнерного пода

Императивный kubectl run создал бы под из трёх полей. Манифест показывает то, что в императивной версии осталось невидимым: лимиты, пробы, политику перезапуска — и главное, документирует, чего в спеке нет.

k8s-anatomy/10-pod-web.yamlPod · фрагмент
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: lab
  labels:
    # метка — ЕДИНСТВЕННЫЙ способ, которым Service, ReplicaSet
    # и NetworkPolicy находят этот под. Имя пода для них не существует.
    app: web
spec:
  # containers — список контейнеров ПРИЛОЖЕНИЯ.
  # Pause-контейнера здесь НЕТ и быть не может: его добавляет runtime.
  containers:
    - name: web        # попадёт в имя docker-контейнера: k8s_<это>_<под>_<ns>_<uid>_<n>
      image: nginx:alpine
      imagePullPolicy: IfNotPresent   # не ходить в реестр, если образ уже на ноде
      ports:
        - name: http
          containerPort: 80       # ВАЖНО: это поле НИЧЕГО не открывает.
                               # Оно чисто информационное — просто документирует,
                               # что процесс слушает 80. Контейнер доступен
                               # по этому порту и без этой строки.
      resources:
        requests:              # читает ПЛАНИРОВЩИК, чтобы выбрать ноду
          cpu: 50m
          memory: 32Mi
        limits:                # читает KUBELET, чтобы настроить cgroup
          cpu: 200m             # превышение CPU -> процесс троттлится
          memory: 128Mi         # превышение памяти -> OOM-killer убивает.
                               # Разное поведение, легко перепутать.
      readinessProbe:          # пока не прошла — IP пода НЕ попадёт
        httpGet:               # в EndpointSlice, Service его не увидит
          path: /
          port: http           # ссылка на ИМЯ порта, объявленное выше
        initialDelaySeconds: 2
        periodSeconds: 5
  restartPolicy: Always    # kubelet поднимет упавший контейнер В ТОМ ЖЕ поде:
                            # podIP сохранится, вырастет restartCount.
                            # Это НЕ то же, что пересоздание пода контроллером.
  terminationGracePeriodSeconds: 5

Второй, с префиксом k8s_POD_, — это и есть материализация понятия "под".

Как читать имена контейнеров k8s_*

схема имениk8s_…
k8s_<контейнер>_<под>_<namespace>_<uid пода>_<restartCount>

k8s_ web _ web _ lab _ 41c157e4-cfc6-4683-b6c1-a30630ca652b _ 0
     └┬─┘  └┬─┘  └┬─┘  └────────────────┬───────────────────┘  └┬┘
   имя     имя    ns          uid пода в etcd            сколько раз
контейнера пода                                    контейнер перезапускался

k8s_POD_… — вместо имени контейнера стоит литерал POD.
Это pause. У него тот же uid, значит он из того же пода.
uid — вот что склеивает строки в под

Не имя, а uid. Две строки с одинаковым uid — это один под. Разные uid — разные поды, даже если имя пода совпадает: пересозданный web получит новый uid, и это будет уже другой объект.

Фильтр docker ps --filter name=web ищет по подстроке, поэтому легко захватывает чужие поды со словом «web» в имени. Формула для самопроверки: строк в выводе = (число подов на этой ноде) × (1 pause + число контейнеров в поде). Не сходится — значит, фильтр поймал лишнее.

Два контейнера в одном поде: случай, где императива нет вообще

kubectl run умеет создать под только с одним контейнером. Многоконтейнерный под описывается исключительно манифестом — это первое место в лекции, где у декларативного подхода просто нет альтернативы.

k8s-anatomy/11-pod-duo.yamlPod · 2 контейнера
apiVersion: v1
kind: Pod
metadata:
  name: duo
  namespace: lab
  labels: { app: duo }
spec:
  containers:
    # Контейнер 1 — сервер. Слушает 80 в ОБЩЕМ для пода netns.
    - name: web
      image: nginx:alpine
      ports:
        - containerPort: 80

    # Контейнер 2 — клиент. Ему НЕ нужно знать IP соседа:
    # сосед доступен по localhost, потому что netns один на двоих.
    - name: shell
      image: busybox:1.36
      # command переопределяет ENTRYPOINT. Без него busybox запустил бы sh,
      # получил EOF на stdin, завершился — и под ушёл бы в CrashLoopBackOff.
      # Контейнер ОБЯЗАН держать процесс живым.
      command: ["sh", "-c", "sleep 3600"]
применить и доказать общий netnskubectl apply -f k8s-anatomy/11-pod-duo.yaml kubectl wait --for=condition=Ready pod/duo -n lab --timeout=90s kubectl exec duo -n lab -c shell -- wget -qO- --timeout=3 http://localhost:80 kubectl exec duo -n lab -c shell -- ip -o addr show eth0 kubectl get pod duo -n lab -o jsonpath='{.status.podIP}{"\n"}'

Два образа, два процесса — но одна сетевая карта на двоих.
Обычные контейнеры Docker так не умеют: у каждого свой netns.
На ноде при этом ТРИ контейнера: pause + nginx + busybox.
Под ≠ контейнер

Под — это сетевой и ресурсный конверт, внутри которого лежат один или несколько контейнеров. На уровне ядра это набор namespace-ов (NET, IPC, UTS общие; PID и MNT обычно свои у каждого контейнера) и общая cgroup-группа с лимитами. Порты внутри пода делятся: два контейнера не могут слушать один и тот же порт, будет «address already in use».

04

Replica и ReplicaSetРеплика — это число, а не объект

Слово «реплика» не обозначает никакой сущности. Это целое число в поле spec.replicas, и ничего больше. Физическое воплощение числа 3 — три пода, и всё.

Логически

Объект ReplicaSet: replicas: N, selector (какие поды считать своими) и template (по какому образцу создавать новые).

Связь «чей это под» хранится не в ReplicaSet, а в самом поде — в поле metadata.ownerReferences. Это указатель снизу вверх, обычное текстовое поле.

Физически

Ничего. Ноль байт на нодах. ReplicaSet — это цикл в процессе kube-controller-manager на control plane.

Цикл: подписаться на события по селектору → посчитать → если меньше N, создать записи Pod; если больше — удалить лишние. Дальше подхватывают планировщик и kubelet.

Голый ReplicaSet: ещё один объект без императивной команды

В боевой практике ReplicaSet руками не создают — его создаёт Deployment. Но чтобы понять, что именно делает Deployment, нужно один раз увидеть слой под ним отдельно. kubectl create такого не умеет: только манифест.

k8s-anatomy/20-replicaset-bare.yamlReplicaSet
apiVersion: apps/v1        # ReplicaSet живёт в группе apps, не в core
kind: ReplicaSet
metadata:
  name: bare
  namespace: lab
spec:
  # Та самая "реплика": ЦЕЛОЕ ЧИСЛО. Отдельного объекта не существует.
  replicas: 3

  # selector — по нему контроллер считает "свои" поды.
  # ВАЖНО: считает ЛЮБОЙ подходящий под, даже созданный не им.
  # Создайте руками под с меткой app=bare — RS усыновит его,
  # а взамен удалит один из своих, чтобы число осталось 3.
  # В apps/v1 это поле ИММУТАБЕЛЬНО — отсюда всё поведение Deployment.
  selector:
    matchLabels:
      app: bare

  # template — образец, по которому штампуются поды.
  # ЖЕЛЕЗНОЕ ПРАВИЛО: метки здесь ОБЯЗАНЫ подходить под selector выше.
  # Иначе контроллер создаст под, не увидит его своим, создаст ещё один,
  # снова не увидит — и так до бесконечности. apiserver такой манифест
  # отклонит с ошибкой "selector does not match template".
  template:
    metadata:
      labels:
        app: bare          # <- обязано матчиться с selector
    spec:
      containers:
        - name: nginx
          image: nginx:alpine

05

DeploymentКонтроллер над контроллером

Deployment не управляет подами. Он управляет ReplicaSet-ами — и в этом весь его смысл. Одна версия шаблона = один ReplicaSet. Обновление = плавный перевод числа реплик из старого RS в новый.

Логически

Объект Deployment: тот же replicas и template, плюс strategy (RollingUpdate с maxSurge / maxUnavailable) и история ревизий.

При каждом изменении template контроллер считает хеш от шаблона и создаёт новый ReplicaSet с этим хешем в имени.

Физически

Снова ничего собственного. Во время обновления на нодах просто сосуществуют процессы двух версий, и их пропорция меняется шаг за шагом.

Откат физически = вернуть счётчик старого RS обратно в N. Старый ReplicaSet не удаляется — он хранится с replicas: 0 именно ради этого.

Манифест: здесь видно всё, что императив скрывает

Команда kubectl create deployment не даёт указать ни стратегию, ни пробы, ни лимиты. А ведь именно strategy определяет, как поведёт себя обновление, и без явного значения вы получите умолчания, о которых не знаете.

k8s-anatomy/30-deployment-shop.yamlDeployment · фрагмент
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
  namespace: lab
  annotations:
    # CHANGE-CAUSE попадает в kubectl rollout history и подписывает ревизию.
    # Без неё в истории будет <none> — и понять, что за ревизия, невозможно.
    kubernetes.io/change-cause: "v1: первичное развёртывание, nginx:alpine"
spec:
  replicas: 3

  # Селектор Deployment. Иммутабелен, как и у ReplicaSet.
  # pod-template-hash сюда НЕ входит — его добавляют только в селектор
  # дочернего RS. Поэтому Service, отбирающий поды по app=shop,
  # во время обновления видит поды ОБЕИХ версий сразу.
  selector:
    matchLabels:
      app: shop

  # strategy — ЭТО ПОЛЕ И ОТЛИЧАЕТ Deployment ОТ ReplicaSet
  strategy:
    type: RollingUpdate     # альтернатива — Recreate: погасить всё, потом поднять
    rollingUpdate:
      maxSurge: 1          # на сколько можно ПРЕВЫСИТЬ replicas -> в пике 4 пода
      maxUnavailable: 0    # сколько готовых подов можно потерять.
                            # 0 => обновление без просадки ёмкости: сначала
                            # поднять новый, дождаться Ready, потом гасить старый.

  revisionHistoryLimit: 3   # сколько старых RS хранить с replicas: 0
                            # ради отката. Умолчание — 10.

  template:
    metadata:
      labels:
        app: shop           # pod-template-hash добавит контроллер сам
    spec:
      containers:
        - name: nginx
          image: nginx:alpine  # ВЕРСИЯ 1. Файл 32- меняет ровно эту строку.
          ports:
            - name: http
              containerPort: 80

          # При maxUnavailable: 0 именно readinessProbe задаёт темп обновления:
          # старый под не погасят, пока новый не отчитается Ready.
          readinessProbe:
            httpGet: { path: /, port: http }
            periodSeconds: 5

          # livenessProbe отвечает на ДРУГОЙ вопрос: "не завис ли процесс".
          #   провал liveness  -> kubelet УБИВАЕТ контейнер и поднимает заново
          #   провал readiness -> под просто выводится из балансировки
          # Путать их опасно: строгая liveness устраивает рестарт-шторм.
          livenessProbe:
            httpGet: { path: /, port: http }
            initialDelaySeconds: 10
            failureThreshold: 3

06

ServiceБалансировщик, которого нет

Поды — расходный материал: имена и IP меняются при каждом пересоздании. Service даёт им одно стабильное имя и один стабильный виртуальный адрес. Вот только адреса этого не существует.

Логически

Объект Service: селектор по меткам, порт и тип. Плюс автоматически создаваемый EndpointSlice — список IP готовых подов.

Имя shop-svc.lab.svc.cluster.local резолвится CoreDNS в фиктивный ClusterIP.

Физически

Правила DNAT в netfilter на каждой ноде. Их пишет kube-proxy, следящий за Service и EndpointSlice.

ClusterIP не назначен ни одному интерфейсу и ни один процесс на нём не слушает. Это просто строка в правиле -d, по которой ядро подменяет адрес назначения на IP живого пода.

k8s-anatomy/40-service-shop-clusterip.yamlService · ClusterIP
apiVersion: v1
kind: Service
metadata:
  name: shop-svc
  namespace: lab
spec:
  type: ClusterIP           # умолчание; адрес виден только ИЗНУТРИ кластера

  # selector работает ТОЛЬКО по меткам: ни имя Deployment,
  # ни имя ReplicaSet здесь не участвуют. Service вообще не знает,
  # что над подами есть какой-то контроллер.
  # pod-template-hash в селекторе НЕТ — поэтому во время rolling update
  # Service отбирает поды ОБЕИХ версий и льёт трафик в них параллельно.
  selector:
    app: shop

  ports:
    - name: http
      port: 80              # порт на ClusterIP — по нему обращаются клиенты
      targetPort: http        # куда переадресовать в поде. Ссылка на ИМЯ порта
                            # из спеки пода — надёжнее числа: поменяете порт
                            # в поде, Service править не придётся.

  # sessionAffinity: ClientIP прибивает клиента к одному поду по IP.
  # Это НЕ решение проблемы долгих соединений (gRPC, WebSocket),
  # а её усиление: балансировка и так происходит раз на соединение.
  sessionAffinity: None

Разберите вероятности

0.333 → 0.5 → без условия. Это не ошибка и не «неравномерность»: правила проверяются по порядку. Первый под получает 1/3 пакетов; из оставшихся 2/3 второй берёт половину — снова 1/3; всё, что дошло до третьего правила, идёт третьему поду. Классический алгоритм равномерного выбора из N вариантов, записанный тремя строками netfilter.

И главное: таблица nat проходится только первым пакетом соединения. Дальше результат живёт в conntrack. Отсюда известная проблема gRPC: одно долгое соединение = одно решение о выборе пода, и kubectl scale нагрузку не перераспределит.

И вторая половина ловушки: kubectl config set-context --current --namespace=lab меняет умолчание только для kubectl. Утилита minikube читает kubeconfig ради адреса кластера, но текущий namespace оттуда не берёт — у неё захардкожен default.

Следствия из устройства Service
  • Это L4, а не L7. Ядро видит TCP/UDP-пакеты, не HTTP-запросы. Роутинг по путям и хостам — задача Ingress.
  • Долгие соединения не перебалансируются. DNAT происходит один раз при установке соединения, дальше conntrack держит его на том же поде. Классическая проблема gRPC и keep-alive.
  • Headless-сервис (clusterIP: None) не создаёт правил вообще — только DNS-записи со списком IP подов. Это и есть штатное решение для клиентской балансировки gRPC.
  • --url работает только с NodePort и LoadBalancer. Для ClusterIP пробрасывать нечего; minikube service list -p calico покажет «No node port».

Rule — четыре разных смыслаОдно слово, четыре механизма

Слово «правило» в Kubernetes перегружено. За ним стоят четыре совершенно разные вещи, которые исполняются в разных местах и разными программами. Разобрать их — значит понять, где вообще проходят границы системы.

Что за правилоГде живёт записьКто исполняетФизически это

RBAC: правило, у которого нет физического воплощения

Role — чистая логика. Никто не пишет ничего в ядро; apiserver просто сверяет запрос со списком в памяти и отвечает «да» или «нет». Это единственный тип правил, целиком остающийся на уровне данных.

k8s-anatomy/50-rbac-pod-reader.yamlSA + Role + RoleBinding
# Три связанных объекта в одном файле через разделитель "---".
# Разрешение без связки бесполезно, связка без учётки не работает —
# для логически неразрывного набора это правильнее трёх файлов.

# --- ДОКУМЕНТ 1: КТО ---
apiVersion: v1
kind: ServiceAccount       # учётка для ПРОЦЕССА, а не для человека
metadata:
  name: viewer               # полное имя в системе прав:
  namespace: lab            #   system:serviceaccount:lab:viewer
---
# --- ДОКУМЕНТ 2: ЧТО МОЖНО ---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role                 # только СПИСОК разрешений, ни к кому не привязан
metadata:
  name: pod-reader
  namespace: lab
rules:
  - apiGroups: [""]        # "" — core-группа. Для Deployment было бы ["apps"]
    resources: ["pods"]    # во МНОЖЕСТВЕННОМ числе, как в URL apiserver
    verbs: ["get", "list", "watch"]
                            # на этих трёх глаголах построена работа
                            # ВСЕХ контроллеров Kubernetes.
                            # create/update/delete отсутствуют — значит запрещены.
                            # Отдельного правила "deny" в RBAC НЕ СУЩЕСТВУЕТ:
                            # модель чисто аддитивная, отобрать доступ можно
                            # только удалив RoleBinding.
  - apiGroups: [""]
    resources: ["pods/log"] # логи — ПОДРЕСУРС пода, отдельный от него.
    verbs: ["get"]          # без этой строки kubectl logs не сработает.
---
# --- ДОКУМЕНТ 3: СВЯЗКА ---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: viewer-can-read
  namespace: lab
subjects:                    # КОМУ выдаём; может быть несколько
  - kind: ServiceAccount     # варианты: ServiceAccount | User | Group
    name: viewer
    namespace: lab
roleRef:                     # ЧТО выдаём; всегда ровно один, поле иммутабельно
  kind: Role                 # Role (этот ns) | ClusterRole (глобальная)
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

NetworkPolicy: правило, которое доезжает до ядра

По умолчанию любой под может обратиться к любому. NetworkPolicy это меняет — но только если установлен CNI с её поддержкой. Императивного эквивалента здесь нет вовсе: kubectl create такого объекта не умеет.

k8s-anatomy/60-networkpolicy-deny-all.yamlNetworkPolicy · запрет
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: shop-deny-all
  namespace: lab
spec:
  # podSelector — к КАКИМ подам применяется политика
  # (а не "кому разрешено"). Пустой {} означал бы "ко всем подам ns".
  podSelector:
    matchLabels:
      app: shop

  # Какие НАПРАВЛЕНИЯ берём под контроль. Только Ingress — значит,
  # исходящий трафик подов shop не ограничен. Добавили бы Egress —
  # пришлось бы отдельно разрешать DNS (порт 53 к kube-dns), иначе
  # не резолвится ни одно имя. Самая частая ошибка новичка.
  policyTypes:
    - Ingress

  # ПУСТОЙ СПИСОК = разрешено ноль источников = запрещено всё.
  # Правил "deny" в NetworkPolicy не бывает; запрет получается
  # как побочный эффект. Внимание на разницу:
  #   ingress: []     <- запрещено всё (пустой СПИСОК правил)
  #   ingress: [{}]   <- разрешено всё (одно ПУСТОЕ правило)
  ingress: []
обязательно в четыре шага# ШАГ 1 — контрольный замер ДО политики. Обязательно делайте шаг 1

Контрольный замер до политики — не формальность. При подготовке оригинальной лекции запрос не проходил ещё до применения запрета: в namespace default с прошлого урока висела политика default-deny-ingress с пустым селектором. Без шага 1 можно было бы решить, что демонстрация удалась. Проверить, не мешает ли что-то: kubectl get networkpolicy -A.

Разрешение поверх запрета: политики складываются

Итоговое разрешение — объединение (OR) всех политик, действующих на под. Приоритетов нет, порядок применения не важен, «последняя побеждает» не бывает.

k8s-anatomy/61-networkpolicy-allow-probe.yamlNetworkPolicy · разрешение
spec:
  podSelector:
    matchLabels:
      app: shop              # тот же адресат, что у политики-запрета
  policyTypes: [Ingress]
  ingress:
    - from:
        # ВНИМАНИЕ НА СИНТАКСИС — самая частая ошибка во всём YAML k8s.
        # Элементы списка from объединяются через ИЛИ,
        # а ключи ВНУТРИ одного элемента — через И:
        #
        #     from:                     from:
        #       - podSelector: {...}      - podSelector: {...}
        #       - namespaceSelector: {}     namespaceSelector: {...}
        #     ^ два элемента: ИЛИ       ^ один элемент: И
        #
        # Лишний дефис меняет смысл правила на противоположный,
        # и никакой ошибки при этом не будет.
        - podSelector:
            matchLabels:
              role: probe      # источник — поды с этой меткой В ЭТОМ ЖЕ ns.
                                # Без namespaceSelector трафик из других
                                # namespace не пройдёт, даже от пода
                                # с точно такой же меткой.
      ports:
        - protocol: TCP
          port: 80              # порт ПОЛУЧАТЕЛЯ, то есть targetPort.
                                # Политика применяется ПОСЛЕ DNAT, когда адрес
                                # и порт уже подменены на подовые.
две одинаковые проверки, разница только в метке клиентаkubectl apply -f k8s-anatomy/60-networkpolicy-deny-all.yaml kubectl apply -f k8s-anatomy/61-networkpolicy-allow-probe.yaml # клиент С меткой role=probe -> проходит kubectl exec probe -n lab -- wget -qO- --timeout=4 http://shop-svc # клиент БЕЗ метки -> таймаут kubectl run no -n lab --rm -i --restart=Never --image=busybox:1.36 -- wget -qO- --timeout=4 http://shop-svc
Если CNI не поддерживает политики

Объект спокойно создастся, kubectl get его покажет, а запрос пройдёт как ни в чём не бывало. Ни ошибки, ни warning, ни события: у NetworkPolicy вообще нет поля status — ей нечем сообщить, что её никто не читает.

Это не поломка, а самая точная иллюстрация принципа всей лекции: запись в etcd без контроллера не делает ничего. Тот же файл в кластере с Calico режет трафик, а с kindnet (умолчание minikube!) остаётся мёртвым текстом. Отсюда и --cni=calico при создании профиля.

Ingress: правило как конфиг чужой программы

Ingress-правила не исполняются Kubernetes вообще. Их читает ingress-контроллер — обычный под с nginx внутри. Он транслирует объект в свой конфиг и перезагружает себя. Физически «правило Ingress» — это блок location в файле nginx.conf внутри чужого пода.

k8s-anatomy/70-ingress-shop.yamlIngress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ing
  namespace: lab
  # Аннотации — способ передать контроллеру настройки, которых нет
  # в стандартной схеме. Префикс определяет, КАКОЙ контроллер их поймёт;
  # для другого эти же строки будут просто проигнорированы.
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  # КАКОЙ контроллер должен взять этот объект. В кластере их может быть
  # несколько. Без этого поля объект подхватит контроллер класса
  # по умолчанию, а если такого нет — НИКТО, и ADDRESS останется пустым.
  # Это самая частая причина "ingress не работает".
  ingressClassName: nginx

  rules:
    - host: shop.local        # правило сработает, только если заголовок Host
                              # равен этому значению. Убрать host —
                              # правило начнёт ловить всё подряд.
      http:
        paths:
          - path: /
            # pathType обязателен. Prefix — по префиксу пути,
            # Exact — полное совпадение, ImplementationSpecific —
            # как решит контроллер (у nginx это включает регулярки).
            pathType: Prefix
            backend:
              service:
                name: shop-svc     # Service ИЗ ЭТОГО ЖЕ namespace. В чужой
                                  # Ingress ходить не умеет — обычная причина 503.
                port:
                  number: 80       # порт Service, НЕ порт пода
поднять контроллер, применить, найти своё правило внутри чужого подаminikube addons enable ingress -p calico kubectl apply -f k8s-anatomy/70-ingress-shop.yaml kubectl get ingress -n lab # в ADDRESS должен появиться IP $ic = (kubectl get pods -n ingress-nginx -l app.kubernetes.io/component=controller -o jsonpath='{.items[0].metadata.name}') kubectl exec -n ingress-nginx $ic -- cat /etc/nginx/nginx.conf | Select-String -Pattern "shop" -Context 2,6
что найдёте
server {
    server_name shop.local ;
    location / {
        set $proxy_upstream_name "lab-shop-svc-80";
        ...

Ваш YAML превратился в обычный кусок nginx-конфига.
Kubernetes здесь только доставил данные — маршрутизирует nginx.
Пустой ADDRESS — единственная подсказка

У Ingress, в отличие от NetworkPolicy, есть поле status. Если kubectl get ingress показывает пустой ADDRESS, значит контроллер объект не подхватил: либо его нет в кластере, либо не совпал ingressClassName. Проверить доступные классы: kubectl get ingressclass.
