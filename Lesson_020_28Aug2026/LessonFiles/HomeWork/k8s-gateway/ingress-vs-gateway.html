01

Почему Ingress оказалось мало

Ingress появился в Kubernetes 1.1 (2015) и до v1 в 1.19 (2020) шёл в статусе beta. Он решал ровно одну задачу: «HTTP-хост и путь → Service». Всё, что выходило за рамки, приходилось делать через аннотации.

Проблема 1

Один объект на всех

Хост, TLS-сертификат, пути и бэкенды лежат в одном ресурсе. Его правит разработчик приложения, хотя сертификат и внешний IP это зона администратора.

Проблема 2

Аннотации вместо API

Rewrite, таймауты, canary, routing по заголовкам делаются через nginx.ingress.kubernetes.io/*. Сменил контроллер на Traefik или HAProxy, и всё это перестало работать.

Проблема 3

Только HTTP

TCP, UDP, gRPC, TLS passthrough в спецификации Ingress отсутствуют. Каждый контроллер придумывал своё.

Проблема 4

Контроллер живёт отдельно

Ingress описывает правила, но не описывает сам балансировщик. Его ставят руками (minikube addons enable ingress), и Kubernetes о нём ничего не знает.

Gateway API это ответ SIG Network на эти четыре проблемы. Он вышел в GA (v1.0) в октябре 2023, стандартные ресурсы стабильны, и Ingress с этого момента официально считается «замороженным»: новых полей в него не добавляют.

Важно

Gateway API это не часть ядра Kubernetes, а набор CRD (Custom Resource Definitions). В Minikube их нет, пока вы их не поставите. В домашке они приезжают вместе с Envoy Gateway одним kubectl apply --server-side.

02

Ролевая модель: три ресурса вместо одного

Главная идея Gateway API: разные люди отвечают за разные слои, значит и ресурсы должны быть разные. Каждый слой ссылается на предыдущий по имени.

Владелец: провайдер / админ кластера

GatewayClass

Cluster-scoped. «Гейтвеи этого класса обслуживает вот такой контроллер». Одно поле, которое имеет значение: controllerName. Аналог IngressClass.

Владелец: платформенная команда

Gateway

Namespaced. «Мне нужна точка входа, слушай HTTP на 80 и HTTPS на 443 с таким сертификатом». Контроллер по этому объекту создаёт реальный прокси. В Ingress аналога нет.

Владелец: разработчик приложения

HTTPRoute

Namespaced. «Запросы на shop.local/* отправляй в Service frontend:80». Это и есть бывший spec.rules из Ingress, но с нормальной схемой вместо аннотаций.

Ключевое отличие

Gateway это заявка на инфраструктуру, а не описание существующей. В Ingress-мире nginx-controller стоял один на кластер и жил своей жизнью. В Gateway API прокси появляется и исчезает вместе с объектом. Это то же самое, что PersistentVolumeClaim для дисков: описал, что нужно, а провижининг сделал контроллер.

03

Путь трафика: что общего, что разное

Пакет от curl до пода фронтенда проходит одни и те же этапы. Разница только в том, кто стоит в роли прокси и в каком namespace он живёт.

04

Один и тот же маршрут двумя языками

Слева файл из прошлой домашки, справа его замена. Обратите внимание: то, что было одним объектом, стало тремя, и каждый короче.

Ingress · 1 файл, 1 объект
k8s/20-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
  namespace: shop
spec:
  ingressClassName: nginx
  rules:
    - host: shop.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80

Хост, путь, бэкенд и класс контроллера в одном месте. Кто отвечает за внешний IP и TLS, из файла не видно.

Gateway API · 3 файла, 3 объекта
k8s-gateway/20-gatewayclass.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: envoy            # без namespace
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
k8s-gateway/21-gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
  namespace: shop
spec:
  gatewayClassName: envoy
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same     # маршруты только из ns shop
k8s-gateway/22-httproute.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop-route
  namespace: shop
spec:
  parentRefs:
    - name: shop-gateway
  hostnames: [shop.local]
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: frontend
          port: 80
Что осталось неизменным

Подсвеченные строки это одни и те же пять фактов: класс контроллера, хост, тип и значение пути, имя и порт Service. Логика маршрутизации не поменялась ни на байт. Изменилась только упаковка.

06

Что меняется в NetworkPolicy

Из четырёх политик прошлой домашки меняется одна: разрешение входа во фронтенд. Причина на схеме в разделе 03: прокси ходит к поду напрямую, значит политика должна пускать конкретные поды прокси из конкретного namespace.

Было: источник ingress-nginx
k8s/31-netpol-frontend.yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: ingress-nginx
    ports:
      - protocol: TCP
        port: 80

Пускаем всё из namespace контроллера. Контроллер там один, этого достаточно.

Стало: источник Envoy-прокси нашего Gateway
k8s-gateway/31-netpol-frontend.yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: envoy-gateway-system
        podSelector:
          matchLabels:
            gateway.envoyproxy.io/owning-gateway-namespace: shop
            gateway.envoyproxy.io/owning-gateway-name: shop-gateway
    ports:
      - protocol: TCP
        port: 80

В namespace прокси может жить несколько Gateway разных команд. Поэтому сужаем до подов, принадлежащих именно нашему.

Ловушка

namespaceSelector и podSelector под одним дефисом это логическое И: «поды с такими метками в таком namespace». Под разными дефисами это ИЛИ: «любой под этого namespace, плюс любой под с такими метками из своего namespace». Вторая запись случайно откроет фронтенд шире, чем нужно.

Что не меняется и почему

  • default-deny-all. Живёт в shop, а прокси в другом namespace. На него политика не действует, ему ничего разрешать не нужно.
  • frontend-egress. Фронтенд по-прежнему ходит только в backend:8080 и DNS. Кто привёл к нему запрос, для исходящих правил не важно.
  • allow-frontend-to-backend. Пускает только app=frontend. Envoy-прокси под этот селектор не попадает, как раньше не попадал nginx-controller. Именно это второй барьер: даже если кто-то опубликует бэкенд через HTTPRoute, политика его не пустит.
  • backend-egress-dns-only. Без изменений.
07

Статусы: где искать причину поломки

У Ingress статус был почти пустой: адрес балансировщика и всё. Если правило не применилось, узнать об этом можно было только из логов контроллера. В Gateway API каждый ресурс носит подробный status.conditions.

РесурсConditionЧто значит False
GatewayClassAcceptedни один контроллер не заявил такой controllerName
GatewayAcceptedкласс не найден или не принят
Programmedконтроллер не смог поднять прокси или сгенерировать конфиг
listeners[].attachedRoutes0 означает: ни один маршрут не прицепился (не тот namespace, hostname не пересёкся)
HTTPRoute (в status.parents[])AcceptedGateway отверг маршрут: allowedRoutes не пускает, hostname не совпал с listener
ResolvedRefsbackendRefs указывает на несуществующий Service, порт или на Service в чужом namespace без ReferenceGrant
Команды
kubectl get gatewayclass                              # колонка ACCEPTED
kubectl -n shop get gateway                           # колонки ADDRESS, PROGRAMMED
kubectl -n shop describe gateway shop-gateway         # Listeners → Attached Routes
kubectl -n shop describe httproute shop-route         # Parents → Conditions
Порядок отладки

Сверху вниз: сначала GatewayClass.Accepted, потом Gateway.Programmed, потом HTTPRoute.Accepted и ResolvedRefs. Если все четыре True, а curl отдаёт 503 или висит, проблема ниже уровня маршрутизации: NetworkPolicy или сам под.

09

Когда что выбирать

Ingress пока уместен
  • Кластер уже живёт на ingress-nginx, и всё, что нужно, это host + path.
  • Helm-чарты сторонних приложений генерируют только Ingress, а вы их не правите.
  • Managed-платформа провайдера ещё не поддерживает Gateway API.
Gateway API стоит брать
  • Новый кластер или новая точка входа: писать новое на замороженном API нет смысла.
  • Нужны canary, header-routing, gRPC, mirror без привязки к одному контроллеру.
  • Несколько команд делят один балансировщик: платформа владеет Gateway, команды владеют своими HTTPRoute.
  • Service mesh: Istio, Linkerd и Cilium используют те же ресурсы для east-west трафика.
Про контроллеры

ingress-nginx Gateway API не поддерживает и не планирует. Поэтому в домашке контроллер заменён на Envoy Gateway. Другие варианты, реализующие Gateway API: NGINX Gateway Fabric (это другой проект, не ingress-nginx), Istio, Cilium, Kong, Traefik v3, а также облачные: GKE Gateway, AWS Load Balancer Controller, Azure Application Gateway for Containers.

10

Проверь себя

Ответы под спойлерами. Сначала подумайте, потом раскрывайте.

1. Удалили объект Gateway. Что произойдёт с подом Envoy-прокси и с HTTPRoute?

Контроллер удалит Deployment и Service прокси: они существовали только ради этого Gateway. HTTPRoute останется в кластере, но в его статусе Accepted станет False с причиной, что родитель не найден. Трафик снаружи ходить перестанет.

2. Почему в NetworkPolicy фронтенда нельзя написать «разрешить от Service envoy»?

NetworkPolicy работает на уровне подов и IP, а не Service. Прокси ходит на Pod IP фронтенда напрямую, а Service это только запись в kube-proxy для исходящих. Селектор источника всегда описывает поды: через podSelector, namespaceSelector или ipBlock.

3. HTTPRoute создан в namespace default, Gateway в shop с allowedRoutes.from: Same. Что увидим?

HTTPRoute.status.parents[].conditions.Accepted = False с причиной NotAllowedByListeners. У Gateway attachedRoutes: 0. Чтобы разрешить, у listener ставят from: All или from: Selector с метками namespace.

4. Разработчик добавил HTTPRoute на backend.local → Service backend. Бэкенд стал доступен снаружи?

Нет. Envoy примет маршрут (ResolvedRefs=True) и попробует соединиться с подом бэкенда, но политика allow-frontend-to-backend пускает только поды с меткой app=frontend. Прокси получит таймаут, клиент увидит 503 или 504. Это и есть смысл двух независимых уровней защиты.

5. Чем GatewayClass отличается от IngressClass по сути, если оба указывают на контроллер?

По сути почти ничем: оба cluster-scoped, оба содержат имя контроллера. Разница в том, что на IngressClass ссылается сам маршрут (Ingress), а на GatewayClass ссылается Gateway, то есть инфраструктурный объект. Разработчик, пишущий HTTPRoute, о классе вообще не знает.

6. curl -H "Host: shop.local" отдаёт 404. Какие два места проверить первыми?

Сначала describe httproute: маршрут должен быть Accepted=True и ResolvedRefs=True. Потом hostnames в HTTPRoute: 404 от Envoy означает, что ни один маршрут не совпал по хосту и пути. NetworkPolicy тут ни при чём: она дала бы таймаут или 503, а не 404.
