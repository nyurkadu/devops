00

Главный принципВсё — это запись плюс контроллер

Почти ни один объект Kubernetes не существует физически. Deployment, ReplicaSet, Service — это JSON-документы в базе etcd. Физически существуют только две вещи: процессы Linux на нодах и правила в ядре этих нод.

Между записью и реальностью стоит контроллер — программа, которая крутит бесконечный цикл: «прочитал желаемое состояние → посмотрел на фактическое → сделал разницу». Вся система построена на этом одном шаблоне, повторённом на каждом уровне.

01

Подготовка средыDocker Desktop как фундамент

Мы используем minikube с драйвером docker. Это важный выбор: при таком драйвере нода кластера — это обычный контейнер Docker Desktop, в который можно зайти и увидеть процессы, cgroups и правила iptables своими глазами. С встроенным Kubernetes самого Docker Desktop так не получится — там поды живут в отдельном namespace containerd и в docker ps не видны.

PowerShellпроверка окружения
# Docker Desktop жив?
docker version --format '{{.Server.Version}}'

# какие профили minikube есть и на каком драйвере
minikube profile list

# поднимаем двухнодовый профиль (первый запуск — несколько минут)
# --cni=calico ОБЯЗАТЕЛЕН: умолчание minikube — kindnet, а он
# NetworkPolicy не исполняет, и секция 07 молча провалится
minikube start -p calico --cni=calico --nodes=2

# переключаем kubectl на этот кластер
kubectl config use-context calico
kubectl get nodes -o wide

# отдельное пространство имён — чтобы не смешаться с прошлыми уроками
kubectl create namespace lab
kubectl config set-context --current --namespace=lab
ожидаемый вывод kubectl get nodes
NAME         STATUS   ROLES           VERSION   INTERNAL-IP
calico       Ready    control-plane   v1.33.1   192.168.58.2
calico-m02   Ready    <none>          v1.33.1   192.168.58.3

Последняя команда делает lab пространством имён по умолчанию — дальше можно не писать -n lab в каждой строке. В конце мы вернём default и удалим весь namespace одной командой.

Если что-то не поднимается

Проверьте, что Docker Desktop запущен и в его настройках выделено хотя бы 4 GB RAM. Для одноузлового варианта достаточно minikube start -p calico --cni=calico — все примеры работают и на одной ноде, просто раздел про размещение реплик по нодам будет менее наглядным. А вот флаг --cni убирать нельзя ни в каком варианте.

Почему --cni=calico нельзя пропустить

По умолчанию minikube ставит kindnet. Сеть подов он поднимет, и первые шесть секций лекции пройдут без единой жалобы — а вот NetworkPolicy он не исполняет. Объект создастся, kubectl get его покажет, kubectl describe напечатает правила, и трафик пойдёт как ни в чём не бывало.

Ни ошибки, ни предупреждения, ни события при этом не будет: у NetworkPolicy вообще нет поля status — ей нечем сообщить, что её никто не читает. Демонстрация в секции 07 провалится молча, и понять почему без этой подсказки практически невозможно.

Проверить, что установлен нужный плагин: kubectl get pods -n kube-system | Select-String -Pattern "calico|cilium|weave". Если профиль уже создан с kindnet, флаг на работающем кластере не применить — CNI задаётся только при создании, профиль придётся пересоздать: minikube delete -p calico, затем команда выше целиком.

02

Node — нодаЕдинственное, что существует по-настоящему

Нода — фундамент всей иерархии. Всё остальное в итоге сводится к тому, что на какой-то ноде запустился процесс.

Логически

Объект Node в etcd. Вы его не создаёте — kubelet при старте сам регистрируется в API и создаёт запись о себе.

В записи: сколько CPU и памяти доступно (capacity / allocatable), метки, taint-ы, условия здоровья (Ready, MemoryPressure). Планировщик читает именно эту запись, а не опрашивает железо.

Физически

Машина с Linux. В проде — сервер или VM. У нас — контейнер Docker Desktop с systemd внутри.

На ней обязательно крутятся три вещи: kubelet (агент, который создаёт контейнеры), kube-proxy (пишет правила в ядро) и container runtime (docker/containerd). Плюс CNI-плагин для сети подов.

Проверяем: нода — это контейнер

PowerShellnode = docker container
# ноды глазами Kubernetes
kubectl get nodes -o wide

# те же самые ноды глазами Docker Desktop
docker ps --filter "name=calico" --format "table {{.Names}}`t{{.Image}}`t{{.Status}}"

# PID контейнера-ноды в вашей системе
docker inspect calico --format '{{.State.Pid}}'
реальный вывод

calico       Ready    control-plane   192.168.58.2   docker://29.2.1
calico-m02   Ready    <none>          192.168.58.3   docker://29.2.1

NAMES        IMAGE                                 STATUS
calico-m02   gcr.io/k8s-minikube/kicbase:v0.0.50   Up 6 minutes
calico       gcr.io/k8s-minikube/kicbase:v0.0.50   Up 7 minutes

Одни и те же имена в двух списках. kubectl показывает их как Node-объекты,
docker ps — как контейнеры. Это один объект, увиденный с двух сторон.

Смотрим, что за демоны живут на ноде

Почему на воркере процессов меньше

Это не сбой и не недонастроенная нода. Разница ровно в роли: calico — control-plane, calico-m02 — обычный воркер. Компоненты управляющего слоя описаны static-манифестами в /etc/kubernetes/manifests/ только на control-plane, и kubelet поднимает их лишь там. Воркер не участвует в принятии решений — он только исполняет поды, которые ему уже назначил планировщик.

Процессcontrol-planeworkerПочему так
kubelet есть есть агент ноды: создаёт контейнеры и регистрирует ноду в API. Нода без него — не нода
dockerd · cri-dockerd · containerd есть есть container runtime. Запускать контейнеры нужно на каждой ноде
kube-proxy есть есть DaemonSet → по поду на каждой ноде. Правила Service нужны везде, откуда ходят в Service
etcd есть нет единственная база кластера. Живёт только на control-plane
kube-apiserver есть нет единственная дверь к etcd. Воркер к нему ходит по сети, а не держит у себя
kube-scheduler есть нет решает, на какую ноду поставить под. Решение принимается централизованно
kube-controller-manager есть нет те самые циклы ReplicaSet/Deployment. Тоже центральный компонент
Ловушка: ps -o comm режет имя до 15 символов

В выводе выше не видно ни kube-scheduler, ни kube-controller-manager — и не потому, что их нет. Причина в grep: паттерн apiserver ловит только apiserver. А kube-controller-manager вдобавок обрезается ядром до kube-controller, потому что comm — это поле длиной 15 символов.

Берите -o args — там полная командная строка без обрезки:

PowerShellчестный список
minikube ssh -p calico -n calico -- "ps -e -o pid,args --no-headers | grep -E 'kubelet|kube-|etcd|dockerd' | grep -v grep"
что на самом деле крутится на control-plane
27763 kube-controller-manager      <- в comm было просто "kube-controller"
27958 kube-scheduler               <- grep 'apiserver' его не ловил
29278 kube-controllers             <- calico-kube-controllers, тоже на CP

Итого не 6 процессов, а 8. Первый вывод был неполным из-за grep,
а не потому, что кластер устроен именно так.
PowerShellроль ноды глазами API
# откуда Kubernetes сам знает, что нода — control-plane: это метка
kubectl get nodes -L node-role.kubernetes.io/control-plane

# те же 4 компонента, но как поды — они видны в kube-system
kubectl get pods -n kube-system -o wide

# сколько ресурсов нода объявила в etcd
kubectl get node calico -o jsonpath='{.status.capacity}'

# метки: по ним планировщик выбирает ноду
kubectl get nodes --show-labels
Запомните флаг -n

В многонодовом кластере minikube ssh -p calico без -n всегда заводит на control-plane. Если ищете контейнеры конкретного пода — сначала узнайте его ноду через kubectl get pod … -o wide, потом заходите именно на неё.

И держите в голове, что этот флаг перегружен: у minikube ssh он означает ноду, а у minikube service и kubectl — namespace. Подробный разбор с типичной ошибкой — в секции 06.

Ключевая мысль

Нода — единственный объект Kubernetes, у которого запись в etcd описывает уже существующую физическую вещь. Все остальные объекты работают наоборот: сначала запись, потом контроллер создаёт под неё реальность.

03

Pod — подНе контейнер, а общий сетевой конверт

Под — минимальная единица, которую планировщик умеет размещать. Kubernetes никогда не планирует отдельный контейнер, только под целиком.

Логически

Объект Pod в etcd: список контейнеров, тома, запросы ресурсов. Плюс поле spec.nodeName — его заполняет планировщик.

Пока nodeName пустой, под находится в состоянии Pending и существует только как запись в базе. Никакого процесса ещё нет.

Физически

Группа процессов Linux на одной ноде, разделяющих сетевой namespace, IPC и (опционально) тома.

Первым runtime запускает крошечный pause-контейнер: он ничего не делает, но держит сетевой namespace. Все остальные контейнеры пода подключаются в namespace этого pause. Поэтому у пода один IP и контейнеры видят друг друга по localhost.

Создаём под и находим его процессы

PowerShellпод → контейнеры
kubectl run web --image=nginx:alpine --port=80
kubectl wait --for=condition=Ready pod/web --timeout=90s

# на какую ноду его положил планировщик
kubectl get pod web -o wide
$node = (kubectl get pod web -o jsonpath='{.spec.nodeName}')
$node

# смотрим контейнеры этого пода именно на ЕГО ноде
minikube ssh -p calico -n $node -- "docker ps --filter name=web --format '{{.Names}}'"
реальный вывод
calico-m02

k8s_web_web_lab_41c157e4-cfc6-4683-b6c1-a30630ca652b_0     <‑ ваш nginx
k8s_POD_web_lab_41c157e4-cfc6-4683-b6c1-a30630ca652b_0     <‑ тот самый pause

Вы просили один контейнер. Runtime создал два.
Второй, с префиксом k8s_POD_, — это и есть материализация понятия "под".

Как читать имена контейнеров k8s_*

Имя контейнера в docker собирается runtime-ом по жёсткому шаблону. Разобрав его, вы узнаёте про под всё, не заходя в kubectl:

схема имениk8s_…
k8s_<контейнер>_<под>_<namespace>_<uid пода>_<restartCount>

k8s_ web _ web _ lab _ 41c157e4-cfc6-4683-b6c1-a30630ca652b _ 0
     └┬─┘  └┬─┘  └┬─┘  └────────────────┬───────────────────┘  └┬┘
   имя     имя    ns          uid пода в etcd            сколько раз
контейнера пода                                    контейнер перезапускался

k8s_POD_… — вместо имени контейнера стоит литерал POD.
Это pause. У него тот же uid, значит он из того же пода.
uid — вот что склеивает строки в под

Не имя, а uid. Две строки с одинаковым uid — это один под. Разные uid — разные поды, даже если имя пода совпадает: пересозданный web получит новый uid, и это будет уже другой объект.

Хвостовой _0 / _2 — это restartCount, он совпадает с колонкой RESTARTS в kubectl get pods.

Ловушка: фильтр по подстроке ловит чужие поды

docker ps --filter name=web — это поиск по подстроке, а не по имени пода. Если в кластере есть ещё что-нибудь со словом «web» на этой же ноде, вы получите вдвое больше строк, чем ожидали:

4 строки вместо 2 — типичная картина
k8s_web_web_lab_1232f174…_0                          <- под web, ns lab
k8s_POD_web_lab_1232f174…_0                          <- его pause
k8s_nginx_web-6c6b8cb6d8-9ffwr_default_fb65bda8…_2   <- ДРУГОЙ под, ns default
k8s_POD_web-6c6b8cb6d8-9ffwr_default_fb65bda8…_2     <- его pause

Два разных uid → два разных пода. Второй — реплика Deployment web,
которую планировщик положил на ту же ноду. 2 пода × 2 контейнера = 4.

Проверка через kubectl подтверждает:
NAMESPACE  NAME                  NODE
default    web-6c6b8cb6d8-9ffwr  calico-m02
lab        web                   calico-m02
PowerShellфильтруем точно
# только контейнеры приложения, без pause
minikube ssh -p calico -n $node -- "docker ps --filter name=web --format '{{.Names}}' | grep -v '^k8s_POD_'"

# только нужный под: имя пода + namespace, а не голая подстрока
minikube ssh -p calico -n $node -- "docker ps --filter name=_web_lab_ --format '{{.Names}}'"

# самый надёжный способ — фильтр по uid пода
$uid = (kubectl get pod web -n lab -o jsonpath='{.metadata.uid}')
minikube ssh -p calico -n $node -- "docker ps --filter name=$uid --format '{{.Names}}'"
Арифметика, которую стоит держать в голове

Строк в docker ps = (число подов на этой ноде) × (1 pause + число контейнеров в поде). Под из одного контейнера даёт 2 строки, под duo ниже — 3. Если цифра не сходится, вы почти всегда захватили фильтром лишний под.

Про jsonpath в PowerShell

Внутри одинарных кавычек PowerShell ничего не подставляет, поэтому перенос строки в jsonpath пишется как {"\n"}, а не через обратный апостроф. А вот в двойных кавычках `t работает как символ табуляции — это разные механизмы, легко перепутать.

Доказываем общий сетевой namespace

Соберём под из двух контейнеров и проверим, что они достучатся друг до друга через localhost — чего два обычных контейнера Docker сделать не могут.

PowerShelltwo-container pod

Два образа, два процесса — но одна сетевая карта на двоих.
Обычные контейнеры Docker так не умеют: у каждого свой netns.
Под ≠ контейнер

Под — это сетевой и ресурсный конверт, внутри которого лежат один или несколько контейнеров. На уровне ядра это набор namespace-ов (NET, IPC, UTS общие; PID и MNT обычно свои у каждого контейнера) и общая cgroup-группа с лимитами.

04

Replica и ReplicaSetРеплика — это число, а не объект

Самая частая путаница на этом уровне: слово «реплика» звучит как имя сущности, но объекта Replica в Kubernetes не существует. replicas: 3 — это просто целое число в спецификации. А копии, которые по нему возникают, — это обычные поды.

ReplicaSet — это объект, и его работа сводится к одному предложению: посчитать поды, подходящие под селектор, и довести их количество до заданного числа. Больше он не делает ничего — ни обновлений, ни откатов.

Логически

Объект ReplicaSet: replicas: N, selector (какие поды считать своими) и template (по какому образцу создавать новые).

Связь «чей это под» хранится не в ReplicaSet, а в самом поде — в поле metadata.ownerReferences. Это указатель снизу вверх.

Физически

Ничего. Ноль байт на нодах. ReplicaSet — это цикл в процессе kube-controller-manager на control plane.

Цикл: подписаться на события по селектору → посчитать → если меньше N, создать записи Pod; если больше — удалить лишние. Дальше подхватывают планировщик и kubelet.

Демонстрация цикла: убиваем под, он воскресает

PowerShellreconcile loop
kubectl create deployment shop --image=nginx:alpine --replicas=3
kubectl rollout status deployment/shop

# три пода — это и есть "три реплики"
kubectl get pods -l app=shop -o wide

# у пода записан его владелец
$pod = (kubectl get pods -l app=shop -o jsonpath='{.items[0].metadata.name}')
kubectl get pod $pod -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'

# убиваем один под и сразу смотрим
kubectl delete pod $pod
kubectl get pods -l app=shop

kubectl get events --sort-by=.lastTimestamp | Select-Object -Last 12
Почему это важно понимать

Под, созданный ReplicaSet-ом, — расходный материал. У него нет постоянного имени, нет постоянного IP и нет памяти о прошлом. Именно поэтому нужен Service: обращаться к подам по IP бессмысленно, они меняются при каждом пересоздании.

05

DeploymentКонтроллер над контроллером

Deployment не управляет подами. Он управляет ReplicaSet-ами — и в этом весь его смысл. Одна версия образа = один ReplicaSet. Обновление = плавный перевод числа реплик из старого RS в новый.

Логически

Объект Deployment: тот же replicas и template, плюс strategy (RollingUpdate с maxSurge / maxUnavailable) и история ревизий.

При каждом изменении template Deployment-контроллер считает хеш от шаблона и создаёт новый ReplicaSet с этим хешем в имени.

Физически

Снова ничего собственного. Во время обновления на нодах просто сосуществуют процессы двух версий, и их пропорция меняется шаг за шагом.

Откат физически = вернуть счётчик старого RS обратно в N. Старый ReplicaSet не удаляется — он хранится с replicas: 0 именно ради этого.

Смотрим rolling update изнутри

PowerShellrollout
# до обновления: один RS
kubectl get rs -l app=shop

# меняем образ — начинается rolling update
kubectl set image deployment/shop nginx=nginx:1.27-alpine
kubectl rollout status deployment/shop

# после: ДВА ReplicaSet
kubectl get rs -l app=shop -o custom-columns='RS:.metadata.name,DESIRED:.spec.replicas,READY:.status.readyReplicas,IMAGE:.spec.template.spec.containers[0].image'

# история ревизий и откат
kubectl rollout history deployment/shop
kubectl rollout undo deployment/shop
kubectl get rs -l app=shop
реальный вывод
RS                DESIRED   READY    IMAGE
shop-56964ffbbb   0         <none>   nginx:alpine         <‑ старый, обнулён
shop-74dc89d55f   3         3        nginx:1.27-alpine    <‑ новый

REVISION  CHANGE-CAUSE
1         <none>
2         <none>

После undo числа меняются местами. Объекты те же самые —
переехало только значение поля replicas. Старый RS не удаляется:
он и есть механизм отката.
Ловите момент

Чтобы увидеть обе версии живыми одновременно, запустите в отдельном окне PowerShell kubectl get pods -l app=shop -w и только потом делайте set image. Появление новых подов и удаление старых пойдут вперемешку — это и есть RollingUpdate на физическом уровне.

06

ServiceБалансировщик, которого нет

Service — самый контринтуитивный объект в Kubernetes. Нет процесса «сервис». Нет виртуальной машины-балансировщика. ClusterIP не назначен ни одному сетевому интерфейсу в кластере: его нельзя пропинговать, у него нет ARP-записи, он не отвечает на трассировку.

Логически

Объект Service: selector, порты, тип. Плюс рядом контроллер endpoints автоматически ведёт объект EndpointSlice — актуальный список IP готовых подов.

Имя shop-svc.default.svc.cluster.local резолвится CoreDNS в тот самый фиктивный ClusterIP.

Физически

Правила iptables (или IPVS) в ядре каждой ноды. Их пишет kube-proxy, который живёт на каждой ноде и следит за Service и EndpointSlice.

Пакет на ClusterIP попадает в цепочку nat, там срабатывает DNAT: адрес назначения переписывается на IP реального пода. Балансировка — это --probability в правиле, а не отдельная программа.

Создаём Service и находим его правила в ядре

PowerShellservice → iptables
kubectl expose deployment shop --port=80 --name=shop-svc
kubectl get svc shop-svc

# вот РЕАЛЬНЫЕ адреса, на которые ведёт DNAT
kubectl get endpointslices -l kubernetes.io/service-name=shop-svc -o wide

# а вот сами правила в ядре ноды
minikube ssh -p calico -n calico -- "sudo iptables-save -t nat | grep shop-svc"
реальный вывод iptables (сокращён)
# 1. вход: пакет на ClusterIP уходит в цепочку сервиса
-A KUBE-SERVICES -d 10.108.35.22/32 -p tcp --dport 80
   -j KUBE-SVC-HU4CVN4KOCHT7JT2

# 2. выбор бэкенда — вот вся "балансировка"
-A KUBE-SVC-HU4CVN4KOCHT7JT2 --comment "shop-svc -> 10.244.15.200:80"
   -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-Z3FN...
-A KUBE-SVC-HU4CVN4KOCHT7JT2 --comment "shop-svc -> 10.244.228.10:80"
   -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-NM7L...
-A KUBE-SVC-HU4CVN4KOCHT7JT2 --comment "shop-svc -> 10.244.228.9:80"
   -j KUBE-SEP-K5KF...

# 3. подмена адреса назначения
-A KUBE-SEP-Z3FN... -p tcp -j DNAT --to-destination 10.244.15.200:80
Разберите вероятности

0.333 → 0.5 → без условия. Это не ошибка и не «неравномерность»: правила проверяются по порядку. Первый под получает 1/3 всех пакетов; из оставшихся 2/3 второй берёт половину — снова 1/3; всё, что дошло до третьего правила, идёт к третьему поду — оставшаяся 1/3. Классический алгоритм равномерного выбора из N вариантов, записанный тремя строками netfilter.

Проверяем, что ClusterIP — фикция

PowerShellвнутри против снаружи
$clusterIP = (kubectl get svc shop-svc -o jsonpath='{.spec.clusterIP}')
$clusterIP

# с Windows-хоста этот адрес недостижим — правил netfilter здесь нет
Test-NetConnection $clusterIP -Port 80 -InformationLevel Quiet

# а изнутри кластера всё работает — и по IP, и по имени
kubectl run tester --rm -it --restart=Never --image=busybox:1.36 -- sh -c "
  nslookup shop-svc;
  wget -qO- --timeout=3 http://shop-svc | head -4"
реальный вывод
10.108.35.22
False                                    <‑ с хоста недостижим, и это правильно

Server:  10.96.0.10
Name:    shop-svc.lab.svc.cluster.local
Address: 10.108.35.22                    <‑ CoreDNS отдал тот же фиктивный IP
<title>Welcome to nginx!</title>        <‑ изнутри пода: работает

Один и тот же адрес: недостижим снаружи, работает внутри.
Разница ровно одна — наличие правил kube-proxy в ядре.
На Windows-хосте этих правил нет, поэтому пакету некуда пойти.

NodePort: то же самое плюс одно правило

PowerShellвыход наружу
kubectl patch svc shop-svc --type=merge -p '{"spec":{"type":"NodePort"}}'
kubectl get svc shop-svc

# minikube пробросит порт с ноды-контейнера на localhost Windows
# -n lab обязателен: minikube НЕ читает namespace из kubeconfig
# команда не завершается — держит туннель, пока не нажмёте Ctrl+C
minikube service shop-svc -p calico -n lab --url

# новое правило в ядре: ловим трафик на порту 3xxxx
minikube ssh -p calico -n calico -- "sudo iptables-save -t nat | grep KUBE-NODEPORTS"
что будет, если забыть -n lab
❌  Exiting due to SVC_NOT_FOUND: Service 'shop-svc' was not found in 'default' namespace.

Хотя kubectl config view --minify -o jsonpath='{..namespace}' честно отвечает "lab".
minikube про этот namespace не знает — см. врезку ниже.
Ловушка: -n значит разное в трёх соседних командах

В этой секции три строки подряд используют флаг -n — и во всех трёх он про разное:

  • minikube ssh -p calico -n calico — это нода;
  • minikube service shop-svc -n lab — это namespace;
  • kubectl get svc -n lab — тоже namespace.

И вторая половина ловушки: kubectl config set-context --current --namespace=lab из секции 01 меняет умолчание только для kubectl. Утилита minikube читает kubeconfig ради адреса кластера, но текущий namespace оттуда не берёт — у неё всегда захардкожен default. Поэтому kubectl get svc shop-svc работает без флага, а minikube service shop-svc в той же сессии падает.

--url работает не для всякого Service

Пробросить наружу можно только NodePort и LoadBalancer. Для ClusterIP пробрасывать нечего — такого адреса вне ноды не существует, о чём вся предыдущая подсекция. Что доступно, показывает одна команда:

PowerShellинвентаризация
minikube service list -p calico
реальный вывод
┌─────────────┬────────────┬──────────────┬─────┐
│  NAMESPACE  │    NAME    │ TARGET PORT  │ URL │
├─────────────┼────────────┼──────────────┼─────┤
│ default     │ kubernetes │ No node port │     │
│ kube-system │ kube-dns   │ No node port │     │
│ lab         │ shop-svc   │ 80           │     │
└─────────────┴────────────┴──────────────┴─────┘

"No node port" = это ClusterIP, --url для него не сработает.
Заодно видно namespace каждого сервиса — тот самый, что нужен для -n.
Следствия из устройства Service
  • Это L4, а не L7. Ядро видит TCP/UDP-пакеты, не HTTP-запросы. Роутинг по путям и хостам — задача Ingress, а не Service.
  • Долгие соединения не перебалансируются. DNAT происходит один раз при установке соединения, дальше conntrack держит его на том же поде. Это классическая проблема gRPC и keep-alive.
  • Headless-сервис (clusterIP: None) не создаёт правил вообще — только DNS-записи со списком IP подов.
07

Rule — четыре разных смыслаОдно слово, четыре механизма

Слово «правило» в Kubernetes перегружено. За ним стоят четыре совершенно разные вещи, которые исполняются в разных местах и разными программами. Разобрать их — значит понять, где вообще проходят границы системы.

Что за правилоГде живёт записьКто исполняетФизически это
iptables rule не объект — производное от Service kube-proxy → ядро строки в netfilter на каждой ноде
NetworkPolicy объект в etcd CNI-плагин (Calico) ещё строки в netfilter/eBPF
Role.rules объект в etcd kube-apiserver ничего — проверка в памяти
Ingress.rules объект в etcd под ingress-контроллера строки в nginx.conf внутри пода

RBAC: правило, у которого нет физического воплощения

Role — это чистая логика. Никто не пишет ничего в ядро; apiserver просто сверяет запрос со списком в памяти и отвечает «да» или «нет». Это единственный тип правил, который целиком остаётся на уровне данных.

PowerShellrbac
kubectl create role pod-reader --verb=get,list,watch --resource=pods

# смотрим само поле rules
kubectl get role pod-reader -o jsonpath='{.rules}' | ConvertFrom-Json | Format-List

# привязываем к сервис-аккаунту
kubectl create serviceaccount viewer
kubectl create rolebinding viewer-can-read --role=pod-reader --serviceaccount=default:viewer

# проверяем решение apiserver — до / после, без единого пакета в сети
kubectl auth can-i list pods    --as=system:serviceaccount:default:viewer
kubectl auth can-i delete pods  --as=system:serviceaccount:default:viewer
вывод
yes
no

Никаких процессов, никаких правил в ядре. Просто apiserver
прочитал Role и RoleBinding из etcd и сравнил со списком.

NetworkPolicy: правило, которое доезжает до ядра

По умолчанию в Kubernetes любой под может обратиться к любому. NetworkPolicy это меняет — но только если установлен CNI с её поддержкой. Без такого плагина объект спокойно создастся в etcd и не даст ровно ничего: некому превратить запись в правила.

PowerShellnetworkpolicy
# есть ли в кластере CNI с поддержкой политик
kubectl get pods -n kube-system | Select-String -Pattern "calico|cilium|weave"

# запрещаем весь входящий трафик к подам shop
@'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: shop-deny-all
spec:
  podSelector:
    matchLabels: { app: shop }
  policyTypes: [Ingress]
  ingress: []
'@ | Out-File -Encoding utf8 deny.yaml

# ШАГ 1 — контрольный замер ДО политики: должно работать
kubectl run t1 --rm -i --restart=Never --image=busybox:1.36 -- wget -qO- --timeout=4 http://shop-svc

# ШАГ 2 — применяем запрет
kubectl apply -f deny.yaml

# ШАГ 3 — тот же запрос теперь должен отвалиться по таймауту
kubectl run t2 --rm -i --restart=Never --image=busybox:1.36 -- wget -qO- --timeout=4 http://shop-svc

# ШАГ 4 — снимаем запрет, доступ возвращается
kubectl delete networkpolicy shop-deny-all
реальный вывод (кластер с Calico)
ДО:     <title>Welcome to nginx!</title>
ПОСЛЕ:  wget: download timed out

Обратите внимание: не "connection refused", а именно таймаут.
Пакет молча уничтожается в ядре — приложение вообще не узнаёт,
что его кто-то заблокировал.
Обязательно делайте шаг 1

Контрольный замер до политики — не формальность. При подготовке этой лекции запрос не проходил ещё до применения запрета: в namespace default с прошлого урока висела политика default-deny-ingress с пустым селектором, блокировавшая вообще всё. Без шага 1 можно было бы решить, что демонстрация удалась.

Поэтому мы и работаем в отдельном namespace lab. Проверить, не мешает ли что-то: kubectl get networkpolicy -A.

Если CNI не поддерживает политики

Объект спокойно создастся, а запрос пройдёт как ни в чём не бывало. Это не поломка, а самая точная иллюстрация принципа всей лекции: запись в etcd без контроллера не делает ничего. Тот же YAML в кластере с Calico режет трафик, а в кластере без поддержки политик остаётся мёртвым текстом.

Ingress: правило как конфиг чужой программы

Ingress-правила (host, path → сервис) не исполняются Kubernetes вообще. Их читает ingress-контроллер — обычный под с nginx или envoy внутри. Он транслирует объект Ingress в свой конфиг и перезагружает себя. Физически «правило Ingress» — это блок location в файле nginx.conf внутри чужого пода.

PowerShellingress
minikube addons enable ingress -p calico
kubectl create ingress shop-ing --rule="shop.local/*=shop-svc:80"

# находим под контроллера и читаем СГЕНЕРИРОВАННЫЙ конфиг
$ic = (kubectl get pods -n ingress-nginx -l app.kubernetes.io/component=controller -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n ingress-nginx $ic -- cat /etc/nginx/nginx.conf | Select-String -Pattern "shop" -Context 2,6
что найдёте
server {
    server_name shop.local ;
    location / {
        set $proxy_upstream_name "default-shop-svc-80";
        ...

Ваше правило Ingress превратилось в обычный кусок nginx-конфига.
Kubernetes здесь только доставил данные — маршрутизирует nginx.

Проверка себя

Если на все пункты отвечаете уверенно — материал усвоен.

  1. Почему после kubectl delete pod появляется под с другим именем, а не тот же самый?
  2. Сколько контейнеров реально запустится на ноде, если в спеке пода описан один?
  3. Почему ClusterIP не пингуется, но wget на него из пода работает?
  4. Где физически находится ReplicaSet — на какой ноде лежат его байты?
  5. Что происходит с NetworkPolicy, если в кластере нет поддерживающего её CNI?
  6. Почему при rolling update kubectl get rs показывает два ReplicaSet, а не один?
  7. Почему длинное gRPC-соединение через Service остаётся на одном поде?
