Ingress и NetworkPolicy

Как запрос снаружи доходит до фронтенда, почему бэкенд при этом остаётся закрытым — и почему запрет «бэк → фронт» не ломает ответы на запросы фронта.

minikube + calico namespace shop ingress-nginx 5 шагов
01

Инфраструктура: кластер, который умеет фильтровать

Minikube — это один узел Kubernetes внутри VM или Docker-контейнера. Кластер настоящий: kube-apiserver, etcd, scheduler, kubelet, CNI-плагин. Не хватает только облачных интеграций — вместо LoadBalancer и облачных дисков идут эмуляции.

minikube start --cni=calico
minikube addons enable ingress

Addon — это не фича Minikube, а заранее подготовленный набор манифестов, который Minikube применяет за тебя. ingress разворачивает ingress-nginx controller — обычный Deployment с nginx внутри, живущий в namespace ingress-nginx. Он слушает 80/443 прямо на IP узла (hostPort), поэтому доступен снаружи по minikube ip.

Грабли 1 · молчаливый провал

Дефолтный CNI в Minikube (kindnet / bridge) не исполняет NetworkPolicy. Объекты создадутся, kubectl get netpol их покажет, а трафик будет ходить как ни в чём не бывало.

NetworkPolicy — это спецификация; исполняет её CNI. Нужен Calico или Cilium, и задать CNI можно только при создании кластера: на живой кластер флаг не накатывается, проще minikube delete и заново.

02

Окружение: namespace — это не файрвол

Namespace даёт изоляцию имён и политик, но не сетевой периметр. Разделение важно понять сразу, иначе половина задания кажется бессмысленной.

Namespace даётNamespace не даёт
Уникальность имён: web в двух ns — два разных объектаИзоляцию сети: под из ns A по умолчанию свободно ходит в ns B
Область действия RBAC, ResourceQuota, LimitRangeОграничение CPU/RAM само по себе
Область действия NetworkPolicyИзоляцию узлов
Массовое удаление: kubectl delete ns shopЗащиту от обращения по FQDN backend.shop.svc.cluster.local
 
kubectl create namespace shop
kubectl config set-context --current --namespace=shop   # чтобы не писать -n везде

NetworkPolicy — объект, привязанный к namespace: она отбирает поды только внутри своего ns. Поэтому Deployment-ы, Service-ы, Ingress и политики кладём в один shop.

03

Приложение: всё держится на метках

Pod — минимальная единица: контейнеры с общим IP и сетевым стеком. Смертен, IP меняется при каждом перезапуске. Deployment держит N реплик и катит обновления. Service — стабильная точка входа: вечный ClusterIP, DNS-имя <svc>.<ns>.svc.cluster.local и список живых Pod IP внутри.

k8s/10-backend.yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: shop
spec:
  type: ClusterIP        # только внутри кластера, наружу не торчит
  selector:
    app: backend
  ports:
    - port: 80           # порт Service
      targetPort: 8080   # порт контейнера

Почему оба сервиса — ClusterIP

ТипКто достучитсяТут
ClusterIPтолько поды кластера✔ фронт и бэк
NodePortлюбой, кто знает IP узла и порт 30000+✕ вторая дверь наружу
LoadBalancerвесь интернет✕

Фронтенд тоже ClusterIP: наружу его выставляет Ingress, а не Service. Сделаешь фронт NodePort — получишь неконтролируемый вход в приложение мимо всей выстроенной маршрутизации.

04

Маршрутизация: одна дверь снаружи

Две сущности, которые постоянно путают:

  • Ingress (объект) — декларация «хост shop.local, путь / → Service frontend:80». Сам по себе это запись в etcd, она ничего не маршрутизирует.
  • Ingress Controller (под) — nginx, который читает все Ingress-объекты через API и переписывает свой конфиг. Вот он и гоняет трафик.

Нет контроллера — Ingress-объект есть, колонка ADDRESS пустая, ничего не работает.

k8s/20-ingress.yaml
spec:
  ingressClassName: nginx
  rules:
    - host: shop.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend   # упомянут ТОЛЬКО фронтенд —
                port:            # правила для backend нет намеренно
                  number: 80

«Доступ снаружи исключительно на фронтенд» достигается отсутствием правила для backend, а не каким-то запретом. Проверка: minikube ip → строка <ip> shop.local в C:\Windows\System32\drivers\etc\hosts → curl http://shop.local.

05

NetworkPolicy: изоляция

Четыре аксиомы
  1. По умолчанию сеть плоская. Любой под ходит к любому поду в любом namespace. Kubernetes — не файрвол «из коробки».
  2. Политика — это whitelist. Как только на под навелась хотя бы одна политика с Ingress в policyTypes, весь входящий трафик к нему запрещён, кроме явно разрешённого. Для Egress — отдельно и независимо.
  3. Политики складываются по ИЛИ. Приоритетов нет, deny-правил в API нет. Две политики на один под — объединение разрешений. Запретить что-то, добавив правило, невозможно: запрещают тем, что не разрешают.
  4. Ingress и Egress независимы. Правило на вход в бэкенд ничего не говорит о его исходящих соединениях.

Почему запрет «бэк → фронт» не ломает ответы

Это тот пункт задания, который выглядит как противоречие: мы запрещаем бэкенду ходить к фронтенду — и при этом фронтенд продолжает получать от бэкенда ответы на свои запросы.

Четыре политики, которые закрывают задание

ФайлНа когоЧто разрешает
30-netpol-default-denyвсе поды nsничего — база изоляции, Ingress + Egress

k8s/30-netpol-default-deny.yaml
spec:
  podSelector: {}          # пустой селектор = ВСЕ поды namespace
  policyTypes: [Ingress, Egress]
k8s/32-netpol-backend.yaml
spec:
  podSelector:
    matchLabels: { app: backend }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: frontend }
      ports:
        - protocol: TCP
          port: 8080       # порт КОНТЕЙНЕРА, не порт Service

Это правило одновременно решает два пункта задания: разрешает фронт → бэк и закрывает прямой внешний доступ к бэкенду — внешний трафик физически приходит от ingress-controller, а он под селектор app=frontend не попадает.

Грабли 2 · namespaceSelector

Он матчится по меткам namespace, а не по имени. Метку kubernetes.io/metadata.name Kubernetes ставит сам, начиная с 1.22 — на неё и опираемся. Проверить: kubectl get ns ingress-nginx --show-labels.

Грабли 3 · какой порт писать

В ports указывается порт пода. Service со своим port: 80 — это DNAT средствами kube-proxy: к моменту фильтрации адрес уже переписан в podIP:8080.

Грабли 4 · потерянный DNS

Как только на поде появляется любая Egress-политика, он теряет доступ к CoreDNS. Симптом: could not resolve host backend, при этом wget podIP:8080 работает. Правило для DNS нужно добавлять в каждую Egress-политику:

    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]

И следи за дефисами: - namespaceSelector и - podSelector двумя элементами списка — это ИЛИ; те же два ключа под одним дефисом — И («под с такой меткой в таком ns»). Один символ меняет смысл правила целиком.

Как читать результат

Timeout / зависание — пакет дропнут политикой, всё правильно. Connection refused — пакет дошёл до узла назначения, политика не сработала: проверяй CNI (kubectl -n kube-system get pods | grep calico) и совпадение меток в селекторах.
