00

Кластер

CNI по умолчанию в Minikube не исполняет NetworkPolicy — правила создадутся, но трафик фильтроваться не будет. Нужен Calico, и выбрать его можно только при создании кластера.

minikube delete
minikube start --cni=calico
minikube addons enable ingress
Флаг --cni на живой кластер не накатывается — если кластер уже поднят без Calico, только пересоздавать.
kubectl -n kube-system rollout status ds/calico-node --timeout=180s
kubectl -n ingress-nginx rollout status deploy/ingress-nginx-controller --timeout=180s
Обе команды должны дойти до successfully rolled out прежде, чем применять манифесты.
01

Развернуть

kubectl apply -f .
kubectl -n shop rollout status deploy/backend
kubectl -n shop rollout status deploy/frontend
12 строк created, затем два успешных rollout.
kubectl -n shop get pods,svc,ingress,netpol
4 пода Running, два Service типа ClusterIP, один Ingress с непустым ADDRESS и четыре NetworkPolicy.
если ADDRESS пустой

Ingress-объект есть, но контроллер его ещё не подхватил. Подожди rollout контроллера и проверь kubectl -n shop describe ingress shop-ingress — там будут события с причиной.

02

Прописать hosts

Ingress маршрутизирует по заголовку Host, поэтому имя shop.local должно резолвиться в IP узла на твоей машине.

minikube ip     # например 192.168.49.2
Windows · PowerShell от администратора
Add-Content C:\Windows\System32\drivers\etc\hosts "`n$(minikube ip) shop.local"
Linux · macOS
echo "$(minikube ip) shop.local" | sudo tee -a /etc/hosts
03

Проверки

Четыре сценария закрывают все требования задания: два должны работать, два — упереться в политику.

Должно работать
curl http://shop.local/
Фронтенд доступен снаружи — Ingress ведёт на него.
Должно работать
curl http://shop.local/api
Тот же путь плюс проксирование фронт → бэк через ClusterIP. Ответ: HELLO FROM BACKEND.
Должен быть timeout
kubectl run probe -n default --rm -it \
  --image=busybox:1.36 --restart=Never -- \
  wget -qO- --timeout=3 \
  http://backend.shop.svc.cluster.local/
Под из чужого namespace под селектор app=frontend не подходит — прямого внешнего доступа к бэкенду нет.
Должен быть timeout
kubectl run bp -n shop --rm -it \
  --image=busybox:1.36 --restart=Never \
  --labels app=backend -- \
  wget -qO- --timeout=3 http://frontend/
Обратный трафик: Egress-политика бэкенда разрешает только DNS.

Ещё две команды, если хочется убедиться изнутри

kubectl -n shop exec deploy/frontend -- wget -qO- http://backend/
curl -s -o /dev/null -w '%{http_code}\n' http://shop.local/backend
Первая печатает ответ бэкенда, вторая — 404 от ingress-контроллера: пути к бэкенду в Ingress просто нет.
как читать результат

Timeout или зависание — пакет дропнут политикой, всё работает правильно.

Connection refused — пакет дошёл до узла назначения, политика не сработала. Проверяй CNI (kubectl -n kube-system get pods | grep calico) и совпадение меток в селекторах.

почему не exec в backend

Напрашивающееся kubectl -n shop exec deploy/backend -- wget ... не сработает: hashicorp/http-echo — образ без shell и без wget, и ты получишь executable file not found вместо честного таймаута.

Поэтому обратный трафик проверяется отдельным busybox-подом, запущенным с меткой бэкенда — --labels app=backend. Под метку попадает — политика к нему применяется.

04

kubectl delete -f .
