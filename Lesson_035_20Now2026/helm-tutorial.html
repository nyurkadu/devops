Helm: практикум для начинающих

Пособие с практическими заданиями для Windows (PowerShell). После каждого задания есть раскрывающийся блок «Ожидаемый результат». Сначала попробуйте сами, потом сверьтесь.

Как пользоваться. Все команды выполняются в PowerShell. Вывод в блоках «Ожидаемый результат» показан примерно: версии, время, хэши и имена подов у вас будут другими. Важна структура и ключевые значения.

0. Что такое Helm

Helm — это пакетный менеджер для Kubernetes. Вместо того чтобы применять десяток YAML-файлов через kubectl apply, вы устанавливаете один пакет.

ТерминЧто означает
Chart (чарт)Пакет: набор шаблонов Kubernetes-манифестов и файл настроек по умолчанию values.yaml.
Repository (репозиторий)Место, где хранятся чарты (как apt- или npm-репозиторий).
Release (релиз)Конкретная установка чарта в кластер под своим именем. Один чарт можно установить много раз под разными именами.
Values (значения)Параметры, которые подставляются в шаблоны: число реплик, образ, порт и т. д.
Revision (ревизия)Номер версии релиза. Каждый install, upgrade или rollback создаёт новую ревизию.

0.1. Что такое чарт

Чарт (chart) — это пакет для Kubernetes: набор файлов, который описывает, как развернуть приложение в кластере. Проще всего понять через аналогию:

Мир Windows / LinuxМир Kubernetes
Установщик программы (.msi, .deb)Чарт
Менеджер пакетов (winget, apt)Helm
Репозиторий пакетовРепозиторий чартов (например, podinfo)
Установленная программаРелиз (установленный чарт, например my-app)

Зачем нужны чарты

Чтобы запустить приложение в Kubernetes, обычно нужно несколько YAML-манифестов: Deployment (поды), Service (сетевой доступ), ConfigMap (настройки), иногда Ingress, Secret и другие. Без Helm их пишут вручную и применяют через kubectl apply по одному. Чарт собирает их в один пакет, и всё ставится одной командой:

helm install my-app podinfo/podinfo

Из чего состоит чарт

mychart/
├── Chart.yaml      # паспорт: имя, версия чарта, версия приложения
├── values.yaml     # настройки по умолчанию (реплики, образ, порт...)
└── templates/      # шаблоны YAML-манифестов
    ├── deployment.yaml
    └── service.yaml

Главная идея: шаблоны и значения

В шаблонах вместо конкретных чисел стоят переменные:

# templates/deployment.yaml
replicas: {{ .Values.replicaCount }}
# values.yaml
replicaCount: 1

При установке Helm подставляет значения в шаблоны и получает готовые манифесты. Поэтому один и тот же чарт можно ставить с разными настройками, не меняя сами шаблоны:

helm install dev  podinfo/podinfo --set replicaCount=1
helm install prod podinfo/podinfo --set replicaCount=5

Две версии у каждого чарта

  • Chart version — версия самого пакета. Меняется, когда меняются шаблоны.
  • App version — версия приложения внутри, например версия образа podinfo.

Обе версии видны в задании 2.3, в колонках CHART VERSION и APP VERSION.

Где вы встретите чарты в пособии: в разделе 3 вы заглянете внутрь готового чарта (helm show values), а в разделе 9 создадите свой (helm create mychart) и увидите его структуру.

1. Подготовка окружения

Helm у вас уже установлен. Для работы ему нужен Kubernetes-кластер и kubectl. На Windows проще всего использовать один из вариантов:

  • Docker Desktop: Settings → Kubernetes → Enable Kubernetes → Apply & restart. kubectl ставится вместе с ним.
  • minikube: winget install Kubernetes.minikube, затем minikube start.

5. Изменение настроек через --set (upgrade)

Чтобы изменить настройки установленного релиза, используется helm upgrade. Флаг --set ключ=значение переопределяет одно значение из values.yaml. Вложенные ключи пишутся через точку: ui.message.

После каждого upgrade и rollback перезапускайте port-forward. port-forward привязывается к одному конкретному поду, даже если вы указали Service. При upgrade или rollback Kubernetes заменяет старые поды новыми (у них другой хэш в имени), старый под удаляется, и туннель закрывается. Тогда curl.exe выдаёт:

curl: (7) Failed to connect to localhost:9898 after 2231 ms: Could not connect to server

Что делать:

  1. Дождитесь, пока новые поды будут в статусе Running: kubectl get pods -n helm-lab.
  2. В окне 1 запустите port-forward заново: kubectl -n helm-lab port-forward svc/my-app-podinfo 9898:9898.
  3. В окне 2 повторите curl.exe http://localhost:9898.

Поле hostname в ответе обычно не меняется между запросами: port-forward всегда ходит в один под, балансировки между репликами здесь нет.

Задание 5.1. Увеличьте число реплик и измените сообщение

Сделайте 3 реплики и задайте своё сообщение.

helm upgrade my-app podinfo/podinfo -n helm-lab --set replicaCount=3 --set ui.message="Hello DevOps"
kubectl get pods -n helm-lab
helm get values my-app -n helm-lab

Задание 5.2. Ловушка: upgrade без --reuse-values

Измените только цвет. Затем проверьте, сколько осталось реплик и что стало с сообщением.

helm upgrade my-app podinfo/podinfo -n helm-lab --set ui.color="#ff5733"
helm get values my-app -n helm-lab
kubectl get pods -n helm-lab
Ожидаемый результат 
Release "my-app" has been upgraded. Happy Helming!
...
REVISION: 3

USER-SUPPLIED VALUES:
ui:
  color: '#ff5733'

NAME                              READY   STATUS    RESTARTS   AGE
my-app-podinfo-5c4d3b2a1f-xxxxx   1/1     Running   0          12s

Реплик снова одна, а сообщение пропало! Если при upgrade передать новые --set, Helm берёт значения по умолчанию из чарта плюс новые значения. Предыдущие --set не сохраняются.

Задание 5.3. Исправьте с помощью --reuse-values

Верните 3 реплики, используя флаг --reuse-values, и убедитесь, что цвет сохранился.

helm upgrade my-app podinfo/podinfo -n helm-lab --reuse-values --set replicaCount=3
helm get values my-app -n helm-lab
Ожидаемый результат 
Release "my-app" has been upgraded. Happy Helming!
...
REVISION: 4

USER-SUPPLIED VALUES:
replicaCount: 3
ui:
  color: '#ff5733'

--reuse-values берёт значения из прошлой ревизии и добавляет новые. В реальной работе надёжнее хранить все настройки в файле и передавать его через -f (следующий раздел).

Другие варианты --set

ПримерЧто делает
--set a=1,b=2Несколько значений в одном флаге через запятую.
--set-string image.tag=1.10Всегда строка. Без этого 1.10 может превратиться в число 1.1.

6. Файлы значений (-f / --values)

В реальных проектах настройки хранят в YAML-файлах в Git: values-dev.yaml, values-prod.yaml. Так видно, что и когда менялось.

Задание 6.1. Создайте файл значений для dev

Создайте файл values-dev.yaml (например, notepad values-dev.yaml) с таким содержимым:

replicaCount: 2
ui:
  message: "Environment: DEV"
  color: "#2e8b57"
resources:
  requests:
    cpu: 50m
    memory: 32Mi
  limits:
    memory: 64Mi

Примените файл:

helm upgrade my-app podinfo/podinfo -n helm-lab -f values-dev.yaml
helm get values my-app -n helm-lab
kubectl get pods -n helm-lab
Ожидаемый результат 
Release "my-app" has been upgraded. Happy Helming!
...
REVISION: 6

USER-SUPPLIED VALUES:
replicaCount: 2
resources:
  limits:
    memory: 64Mi
  requests:
    cpu: 50m
    memory: 32Mi
ui:
  color: '#2e8b57'
  message: 'Environment: DEV'

NAME                              READY   STATUS    RESTARTS   AGE
my-app-podinfo-...-aaaaa          1/1     Running   0          10s
my-app-podinfo-...-bbbbb          1/1     Running   0          10s

Аннотация и NodePort из задания 5.4 пропали, потому что их нет в файле. Это та же логика, что в задании 5.2.

Задание 6.2. Приоритет значений

Передайте одновременно файл и --set с другим числом реплик. Предскажите результат до запуска.

helm upgrade my-app podinfo/podinfo -n helm-lab -f values-dev.yaml --set replicaCount=4
kubectl get deploy my-app-podinfo -n helm-lab
Ожидаемый результат 
Release "my-app" has been upgraded. Happy Helming!
...
REVISION: 7

NAME             READY   UP-TO-DATE   AVAILABLE   AGE
my-app-podinfo   4/4     4            4           20m

Приоритет от низшего к высшему: values.yaml чарта → файлы -f (каждый следующий важнее предыдущего) → --set. Поэтому реплик 4.

Задание 6.3. upgrade --install

Команда helm upgrade --install устанавливает релиз, если его нет, и обновляет, если он уже есть. Её часто используют в CI/CD. Установите второй релиз my-app-2 этой командой.

helm upgrade --install my-app-2 podinfo/podinfo -n helm-lab --set ui.message="Second release"
helm list -n helm-lab

Задание 9.2. Добавьте свой шаблон ConfigMap

Создайте файл mychart\templates\configmap.yaml:

apiVersion: v1

  labels:
    {{- include "mychart.labels" . | nindent 4 }}
data:
  greeting: {{ .Values.greeting | quote }}
  environment: {{ .Values.environment | default "dev" | quote }}

greeting: "Hello from mychart"

11. Итоговое задание

Выполните самостоятельно, не подглядывая в разделы выше:

  1. Создайте namespace final.
  2. Снова добавьте репозиторий podinfo и обновите индекс.
  3. Создайте файлы values-staging.yaml (2 реплики, сообщение «STAGING», цвет #d48806) и values-prod.yaml (3 реплики, сообщение «PROD», цвет #c0392b).
  4. Установите релиз shop с настройками staging.
  5. Обновите его до prod, а затем через --set измените только сообщение на «PROD v2», не потеряв остальные значения prod.
  6. Откатитесь на staging-ревизию.
  7. Покажите историю и убедитесь, что откат создал новую ревизию.
  8. Удалите релиз, namespace и репозиторий.
Решение и ожидаемый результат 
kubectl create namespace final
helm repo add podinfo https://stefanprodan.github.io/podinfo
helm repo update

helm install shop podinfo/podinfo -n final -f values-staging.yaml
helm upgrade shop podinfo/podinfo -n final -f values-prod.yaml
helm upgrade shop podinfo/podinfo -n final -f values-prod.yaml --set ui.message="PROD v2"
helm rollback shop 1 -n final
helm history shop -n final

helm uninstall shop -n final
kubectl delete namespace final
helm repo remove podinfo

История должна выглядеть так:

REVISION  STATUS      DESCRIPTION
1         superseded  Install complete
2         superseded  Upgrade complete
3         superseded  Upgrade complete
4         deployed    Rollback to 1

В шаге 5 тоже можно было написать --reuse-values --set ui.message="PROD v2". Но вариант с повторной передачей файла надёжнее: итоговые значения всегда видны из команды.
